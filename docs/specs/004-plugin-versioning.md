# SPEC-004: Версионирование и релизы плагина

Статус: approved

## Зачем

Кит распространяется как плагин Claude Code, и потребитель через
GitHub-маркетплейс получает не HEAD репозитория, а снапшот в локальном
кэше, версионированный по `plugin.json`. Версия кита не бампалась ни разу
(`0.1.0` навсегда): ralph, конфиг, все гейты «живут внутри 0.1.0» — для
механики кэша обновлять нечего, для человека нет ни сигнала об
изменениях, ни списка «что нового», а проект, подключивший кит с GitHub,
молча отстаёт от main без какого-либо признака отставания. Нужен
механический релизный процесс: версия растёт сама по правилам, релизы
собираются из уже существующей конвенции истории main, потребитель имеет
одну документированную команду обновления.

## Что делаем

### Политика бампа: механическая, трёхуровневая

- **patch** — каждый PR в main, меняющий файлы плагина (commands/,
  agents/, skills/, hooks/, templates/, plugin.json): в ките почти любой
  файл — это поведение потребителя, включая md-инструкции команд.
  PR только по docs/specs/, docs/adr/, docs/plans/, docs/observability/
  и tests/ версию не бампает — это артефакты процесса самого кита,
  потребителю они не отгружают поведение.
- **minor** — закрытие вехи (SPEC-NNN или CONS-NNN): бамп делает
  `/consolidate` на границе вехи, тем же шагом, что закрывает milestone.
- **major** — ломающее изменение контракта с проектами (переименование
  `scripts/check|test|fix`, несовместимая смена схемы журнала или
  формата `adk.config.json`); до 1.0.0 допустим minor с явной пометкой
  breaking в релизе.

### Гейт бампа

PR, меняющий файлы плагина, обязан менять `version` в `plugin.json` —
иначе CI-гейт красный с внятным сообщением («изменены файлы плагина —
бампни version»). Сравнение — с base-веткой PR; правило и перечень
«файлов плагина» — в docs/contract.md. Локальные гейты (scripts/check)
это не проверяют: сравнение с базой требует сети/истории, это работа CI.

### Релизы из истории, без рукописного CHANGELOG

История main кита — уже changelog: squash-заголовок = «глагол +
результат (#N)». Рукописный CHANGELOG.md не заводим (второй источник
правды, который дрейфует). Вместо него: CI-workflow на push в main
замечает изменение `version` → ставит git-тег `vX.Y.Z` → создаёт GitHub
Release с notes из заголовков коммитов от прошлого тега. Релиз — это
генерируемый артефакт конвенции, а не отдельный труд.

### Обновление потребителя: одна команда, две ступени

README (раздел установки) документирует:
- подключение через GitHub-маркетплейс (пример settings.json) и
  обновление: `claude plugin update agent-dev-kit@agent-dev-kit`;
- **двухступенчатость**: обновление плагина не обновляет проектные
  артефакты (копия `scripts/ac-check`, CI, конфиг) — вторая ступень
  описана правилом contract.md (появилось в #56/#118), README на него
  ссылается, а не пересказывает.

### Версия в наблюдаемости

`adk-ralph.sh` и `/autopilot` пишут версию плагина в `event=run_start`
журнала — сводка и разбор инцидентов всегда знают, на какой версии шёл
прогон (расширение схемы ADR-001 полем, как с `tokens`).

## Границы

- Никакой публикации во внешние каталоги/маркетплейсы — только
  GitHub-репозиторий кита.
- Никакого автообновления проектных копий (`scripts/ac-check` и т.п.) —
  вторая ступень остаётся ручной по правилу contract.md.
- Никаких semver-гарантий стабильности API до 1.0.0 — до неё major не
  используется, ломающие изменения помечаются в релизе.
- Рукописный CHANGELOG.md не заводится (см. «Релизы из истории»).
- Автобамп ботом (без участия автора PR) не делаем: бамп — часть диффа
  PR, видимая на ревью, а не пост-фактум магия.

## Критерии приёмки

- [ ] AC-1 (ждёт #151): CI-гейт падает на PR, который меняет файлы плагина
      (commands/agents/skills/hooks/templates/plugin.json), не меняя
      `version`; PR только по docs/specs|adr|plans|observability и
      tests/ проходит без бампа; сообщение гейта называет правило.
- [ ] AC-2: push в main с изменённым `version` создаёт git-тег `vX.Y.Z`
      и GitHub Release, notes которого содержат заголовки коммитов от
      предыдущего тега; push без изменения `version` тега не создаёт.
- [ ] AC-3: политика бампа (patch/minor/major, перечень «файлов
      плагина») зафиксирована в docs/contract.md; `/consolidate` на
      границе вехи бампает minor тем же шагом, что закрывает milestone.
- [ ] AC-4: README документирует подключение через GitHub-маркетплейс,
      команду обновления и двухступенчатость (со ссылкой на правило
      contract.md об обновлении проектных копий).
- [ ] AC-5 (ждёт #154): `event=run_start` в журнале ralph и `/autopilot` содержит
      версию плагина; `/stats` не ломается на старых записях без поля.
- [ ] AC-6 (ждёт #156): первый релиз по новой политике ставит тег на текущий main
      без переписывания истории; вся предыдущая история остаётся без
      тегов и попадает в notes первого релиза одним списком.

## Переходные состояния

Гейт бампа включается на репозитории, где ни один прошлый PR версию не
бампал: он действует только на новые PR, история не переоценивается.
Вся накопленная история до первого тега — один «пре-релиз»: первый тег
ставится на текущее состояние main (AC-6), его notes вбирают прошлые
заголовки одним списком. Потребители, сидящие на кэше `0.1.0`,
обновляются той же документированной командой — принудительного сигнала
им кит послать не может (граница механики Claude Code), поэтому команда
обновления и попадает в README на видное место.
