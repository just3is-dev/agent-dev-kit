# SPEC-002: Профили процесса

Статус: draft

## Зачем

Политика процесса зашита в кит намертво: merge после APPROVE агента,
автопилот мержит сам, конвенций коммитов и типов задач нет. Один флоу не
подходит всем проектам: в личном проекте агенты пишут и мержат сами; на
работе обязательно ревью коллеги-человека, приняты свои конвенции, а
серверные настройки репозитория управляются не нами. Нужна per-project
конфигурация политики и конвенций: задаётся при инициализации, меняется
явным коммитом — перевод любого гейта из «человек обязателен» в
«человек наблюдает» становится видимым решением с историей, а не
поведением по умолчанию.

## Что делаем

**Конфиг `adk.config.json` в корне проекта.** Коммитится (политика —
разделяемая правда команды, в отличие от журнала `.adk/`). Генерируется
`/project-init` по выбранному профилю; существующий файл никогда не
перезаписывается. Отсутствие файла = профиль solo — полная обратная
совместимость с текущим поведением.

**Профили — пресеты полей** (любое поле переопределяемо вручную):

| Поле | solo | team | locked |
|---|---|---|---|
| policies.merge | agent-after-approve | human-review-required | human-only |
| policies.review.humanApprovalRequired | false | true | true |
| policies.review.maxRounds | 2 | 2 | 1 |
| policies.autopilot.enabled / canMerge | true / true | true / false | false / — |
| серверные настройки репо | настраиваем | читаем, не трогаем | читаем, не трогаем |

**Блок policies:**
- `merge`: `agent-after-approve` (текущее: ready-PR мержит кто угодно,
  включая автопилот) | `human-review-required` (merge только при
  человеческом approve на PR) | `human-only` (merge из агентских сессий
  запрещён всегда — только руками человека вне процесса).
- `review`: `maxRounds` (лимит кругов до эскалации), `humanApprovalRequired`.
- `autopilot`: `enabled`, `canMerge`, `maxTasksPerRun`.

**Блок conventions:**
- `mergeStrategy`: `squash | merge | rebase`. Концептуально это две оси —
  гранулярность (схлопнуть коммиты ветки / сохранить) и граф (линейный /
  с merge-узлами); enum из трёх — проекция GitHub, оставлена ради
  1:1-маппинга на серверные `allow_*_merge`. Дефолт solo — squash:
  внутриветочные коммиты агента — черновики, main читается как чейнджлог.
- `branchUpdate`: `rebase | merge-from-main` — как актуализировать ветку
  под уехавший main перед merge; после актуализации гейты перегоняются
  обязательно.
- `commitStyle`: `conventional | plain`; `language`; `branchPattern`
  (дефолт `issue-{n}-{slug}`).
- `attribution`: добавлять ли trailer `Co-Authored-By: Claude` (прозрачность
  соавторства машины; на работе может быть обязателен, в персональных
  проектах — по вкусу).

**Блок types — типизация work items.** Тип задачи — сквозная сущность:
задаётся label'ом при создании issue и дальше наследуется автоматически,
никто ничего не «угадывает из текста»:

- `types.<имя>`: `label`, `commitType`, `requiredFields`. Дефолтные типы:
  `task` (label `type:task`, commitType `feat`; поля Контекст/Сделать/DoD
  с AC-ссылками/Зависит от), `bug` (`type:bug`, `fix`; Воспроизведение /
  Ожидаемое / Фактическое / «Сбежал от: <гейт>»), `fastFollow`
  (`type:fast-follow`, `fix`; Источник: вердикт ревью PR #N),
  `consolidate` (`type:consolidate`, `refactor`).
- Наследование по цепочке: `/plan` ставит `type:task` создаваемым issues
  (labels создаются в репо при отсутствии) → `/work` читает label и
  применяет правила типа (bug — репро-тест первым; task — AC-теги;
  consolidate — поведение не меняется) → заголовок PR получает
  `commitType` типа → squash-коммит в main типизирован → журнал пишет
  тип → `/stats` и агрегация «Сбежал от» в `/consolidate` режут по типу.
- `.github/ISSUE_TEMPLATE/*` генерируются из types при `/project-init` —
  люди в команде создают issues в том же формате, что и агенты.

**Enforcement — три слоя:**
1. **Хуки читают конфиг** (жёстко): bash-guard — политика merge
   (`human-only` → блок всегда; `human-review-required` → merge только при
   `reviewDecision == APPROVED`); при `commitStyle=conventional` —
   валидация заголовка PR на `gh pr create`/`gh pr edit` по шаблону
   `<commitType>[(scope)]: <суть> (#N)` с commitType, соответствующим
   label'у issue. Внутриветочные коммиты не валидируются — squash их
   схлопывает, точка контроля одна: заголовок PR.
2. **Сервер** (жёстче всех): `/project-init` для нового репозитория
   настраивает allowed merge methods по mergeStrategy,
   `delete_branch_on_merge=true`, branch protection по профилю,
   ISSUE_TEMPLATE. Для существующего репозитория (типично team) —
   настройки читаются, расхождения с конфигом сообщаются, ничего не
   перезаписывается.
3. **Инструкции команд** (мягко): формулировки отчётов соответствуют
   политике («PR готов к ревью коллеги» vs «смержено»).

## Границы

- Никаких расписаний, ночных прогонов и параллельности — это SPEC-003
  «Автономия»; здесь только конфиг-поля, которые она будет читать.
- Существующие issues задним числом не типизируются; валидация заголовков
  применяется к новым PR.
- Серверные линтеры (commit-lint, PR-title-check) не переизобретаем:
  если они есть, локальная валидация отключается полем конфига.
- Конфиг per-project; глобального пользовательского уровня нет.
- Механизм чтения конфига хуками — bash + python3, как весь кит; никакой
  новой зависимости.

## Критерии приёмки

- [ ] AC-1: `/project-init` предлагает выбор профиля (solo/team/locked) и
      создаёт `adk.config.json` с пресетом; существующий конфиг не
      перезаписывается; проект БЕЗ конфига ведёт себя как solo — текущие
      тесты кита проходят без изменений поведения.
- [ ] AC-2: bash-guard уважает `policies.merge`: `human-only` — `gh pr
      merge` блокируется даже для ready-PR; `human-review-required` —
      merge разрешён только при человеческом approve (тестовый обход —
      env-переменная, как ADK_GUARD_PR_STATE); `agent-after-approve` и
      отсутствие конфига — поведение как сейчас (фикстурные тесты на все
      три политики).
- [ ] AC-3: `/autopilot` читает `policies.autopilot`: `enabled=false` —
      отказ старта с объяснением; `canMerge=false` — ready-PR не мержатся
      и перечисляются в отчёте как «ждут человека»; `maxTasksPerRun`
      ограничивает прогон.
- [ ] AC-4: `/plan` создаёт issues с label типа task (labels в репо
      создаются при отсутствии); `/work` определяет тип по label и
      применяет правила типа; issue без label обрабатывается как task.
- [ ] AC-5: при `commitStyle=conventional` bash-guard отклоняет
      `gh pr create` с заголовком, не соответствующим
      `<commitType>[(scope)]: <суть> (#N)` или с commitType, не
      соответствующим label'у issue; при `plain` и без конфига — не
      вмешивается.
- [ ] AC-6: `/project-init` в новом репозитории настраивает сервер по
      конфигу (merge methods, delete_branch_on_merge, protection,
      ISSUE_TEMPLATE); в существующем — сверяет и сообщает расхождения,
      не меняя ничего.
- [ ] AC-7: журнал прогонов содержит тип задачи; `/stats` выводит разрез
      по типам (задачи/баги: количество, средние круги ревью).
- [ ] AC-8: перед merge неактуальной ветки (BEHIND/CONFLICTING относительно
      main) `/work` и `/autopilot` актуализируют её способом из
      `conventions.branchUpdate` и перегоняют гейты; merge без перегона
      гейтов после актуализации невозможен по инструкции.

## Решённые вопросы

- **Squash уже внедрён** (2026-08-07) как дефолт в командах и серверно
  (оба репозитория — squash-only, заголовок squash = заголовок PR);
  спека формализует это как значение конфига, а не меняет поведение.
- **Автоудаление веток** после merge включено серверно (2026-08-07);
  `--delete-branch` в командах остаётся как страховка для репозиториев,
  где серверная настройка недоступна.
- **Label — единственный источник типа**: тип не выводится из текста
  issue; отсутствие label = task (безопасный дефолт).
- **Валидация конвенции — только заголовок PR**, не каждый коммит ветки:
  при squash содержимое веточных коммитов исчезает, а единственная точка
  контроля дешевле и надёжнее.
- **enum mergeStrategy** — сознательная проекция GitHub (см. блок
  conventions) вместо двух «чистых» осей.
