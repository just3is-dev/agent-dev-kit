# ADR-006: swift-ios — шаблон не везёт каркас приложения, типы таргетов проверяются в test

Дата: 2026-08-15
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Два открытых вопроса шаблона swift-ios (issue #70). Первый: для
node/python `/project-init` создаёт каркас пустого проекта штатным
генератором, у iOS штатного CLI-генератора нет — либо шаблон везёт
минимальный `project.yml` + скелет `App/`, либо каркас пишется по месту.
Второй: компиляция таргетов приложения (`xcodebuild build`) стоит минуты,
а контрактный `check` зовётся PostToolUse-хуком после каждой правки и
обязан быть быстрым (docs/contract.md: цель < 30 сек по файлам).

## Решение

1. Шаблон везёт только контракт (`scripts/`), CI и конфиг форматтера.
   Каркас пустого iOS-проекта (`project.yml` для XcodeGen, точка входа)
   агент пишет по месту под конкретный проект — как для «другого стека».
   Кит не диктует структуру проекта ни одному стеку: для node/python
   структуру задаёт штатный генератор экосистемы, а не шаблон кита;
   зашить скелет в шаблон значило бы сделать кит владельцем чужого
   архитектурного решения.
2. Проверка типов в `check` — только `swift build` SPM-пакетов (секунды).
   Компиляция таргетов приложения живёт в `scripts/test` как smoke
   «приложение собирается» (аналог bootstrap-теста сервиса из контракта).
   Размен осознанный: ошибка компиляции в SwiftUI-коде таргета всплывает
   не на PostToolUse-гейте, а на Stop-гейте (stop-test) — позже на
   минуты, но в пределах того же хода агента.

## Последствия

- Плюс: шаблон одинаково ложится на любой существующий iOS-проект,
  ничего не навязывая; `check` остаётся быстрым гейтом.
- Минус: у пустого iOS-проекта первый шаг дороже (агент пишет каркас
  сам); ошибки в коде таргетов ловятся Stop-гейтом, а не после каждой
  правки. Вынос логики в SPM-пакеты (рекомендация скилла tdd) возвращает
  посимвольную скорость проверки типов там, где идёт основная работа.
