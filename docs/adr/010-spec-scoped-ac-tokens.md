# ADR-010: AC-токен привязан к спеке литералом `AC-<NNN>-<K>`, не разбором имени файла

Дата: 2026-09-14
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

`ac-check.sh` собирал `AC-<K>` в один глобальный пул по всем approved-спекам
(issue #171): тест с тегом `AC-3` засчитывал покрытие критерия 3 любой
спеки, где такой номер встречался. У двух спек со случайно совпавшим
номером критерия покрытие одной маскировало отсутствие покрытия у другой.
ADR-009 (issue #172) уже отмечал, что в самом ките это ни разу не
проявлялось видимым образом только из-за этой коллизии.

Нужно было решить два вопроса: (1) как новый токен привязывает критерий к
конкретной спеке и (2) как парсер `ac-check.sh` сопоставляет тег теста с
номером спеки — по имени файла спеки (`docs/specs/NNN-слуг.md`) или по
числу, встречающемуся литералом и в спеке, и в тесте.

## Решение

Токен — `AC-<NNN>-<K>` (например `AC-002-3`): `NNN` — номер спеки, `K` —
порядковый номер критерия внутри неё. `NNN` — часть текста самого токена,
переписанная в спеке и в тесте одинаково; парсер сравнивает токены
**литеральной строкой** (`grep -oE 'AC-[0-9]+(-[0-9]+)?'` + сопоставление
через `grep -qxF`), не разбирает имя файла спеки и не извлекает из него
номер. Привязка к спеке возникает из совпадения строки токена, а не из
внешнего сопоставления «файл → номер».

Обратная совместимость: голый `AC-<K>` без второй группы цифр
по-прежнему собирается в старый глобальный пул (ровно прежнее поведение)
— существующие проекты не мигрируют принудительно. `ac-check.sh` печатает
предупреждение (число голых токенов, без перечисления самих номеров —
конкретные номера неотличимы от списка непокрытых критериев в том же
выводе и засорили бы grep-проверки по нему), но не падает и не требует
миграции для зелёного гейта.

Отклонённые альтернативы:
- **Извлекать NNN из имени файла спеки** (`docs/specs/NNN-слуг.md`) и
  сверять его с номером в самом токене — отклонено: усложняет парсер без
  выигрыша (привязка и так возникает из литерального совпадения строки),
  требует спеку с числом в имени файла (кит уже допускает произвольные
  имена — регрессия для спеки без номера в имени), и превращает
  расхождение «токен ссылается не на свою спеку» в тихий баг парсера
  вместо явной опечатки автора спеки/теста.
- **Сквозная нумерация конвенцией** (вариант 2 issue #171, без кода) —
  отклонено по рекомендации issue: не лечит корень (гейт всё ещё слеп к
  принадлежности критерия), рассыпается при первой перенумерации, требует
  от планировщика помнить «последний занятый номер» через все спеки.

## Последствия

- Спека и её тесты дальше сами отвечают за то, что префикс `NNN` в токене
  совпадает с её собственным номером — `ac-check.sh` эту связь не
  проверяет отдельно (как и раньше не проверял, что номер критерия в
  тесте соответствует его сути по смыслу — это остаётся на ревьюере,
  чек-лист `agents/reviewer.md` обновлён явным пунктом).
- Существующие approved-спеки кита (`docs/specs/001-004`) и его тесты
  (`tests/run.sh`) **не мигрированы** на `AC-<NNN>-<K>` этим PR — issue
  #171 явно не требует этого для DoD, а кит опирается на бытовое ревью,
  а не на гейт, для соответствия тега сути критерия. Расследование
  показало, что коллизия у кита не гипотетическая: каждый непомеченный
  «ждёт #N» номер критерия 1–8 встречается более чем в одной спеке
  (например AC-4 — в 001, 002 и 004 одновременно) — то есть при миграции
  без сверки фактического покрытия каждой спеки часть критериев рискует
  оказаться реально непокрытой отдельным тестом. Мигрировать теги кита —
  отдельная, самостоятельная по объёму задача (аудит соответствия тега
  сути критерия для каждой спеки), вынесена за рамки этого PR намеренно,
  не как недосмотр.
- Новые спеки, созданные `/spec` после этого решения, получают
  `AC-<NNN>-<K>` по шаблону (`templates/process/spec-template.md`) —
  коллизия номеров для них по построению невозможна.
