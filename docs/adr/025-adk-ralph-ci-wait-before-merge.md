# ADR-025: adk-ralph.sh — ожидание зелёного CI перед merge актуализированной ветки

Дата: 2026-10-10
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

Заменяет п.4 ADR-019 («CI-watch сознательно не реализован»); остальные
пункты ADR-019 в силе.

## Контекст

`resolve_ready_pr` (ADR-019) после актуализации ветки перегоняет ЛОКАЛЬНЫЕ
гейты, делает `git push` и сразу мержит — не дождавшись отчёта CI на
GitHub по этому push. Только что запушенная голова ещё ни разу не
проверялась CI: смерженная ветка с красным `gates`/`version-bump-check`
возможна (issue #196). Канон — шаг 3 `commands/autopilot.md`: «если
настроен CI — дождись зелёного перед merge; это же покрывает CI-прогон
актуализированной ветки». ADR-019 §4 отложил это из-за двух трудностей:
надёжно отличить «CI не настроен» от «CI ещё не зарегистрировался» и
разных кодов выхода `gh pr checks` на «нет проверок»/«pending»/«fail».

## Решение

1. **Когда ждём — только если этим прогоном ветка актуализирована и
   запушена** (внутри ветки `behind > 0` `resolve_ready_pr`, сразу после
   успешного push). Ветка, которую ralph не трогал, мержится как раньше:
   её CI отчитался до перевода в ready.
2. **Источник статуса — `gh pr view <PR> --json headRefOid,statusCheckRollup`,
   не `gh pr checks`.** `gh pr checks` (в том числе с `--json`) отдаёт
   ненулевой exit на pending (8) и на fail (1) и по-разному ведёт себя на
   «проверок нет» в разных версиях `gh`; отличить это от настоящего
   сбоя `gh` по коду нельзя. `gh pr view --json` — exit 0 и JSON объект
   (пустой `statusCheckRollup` на «проверок нет») или ненулевой exit =
   сбой; единственный сигнал успеха — exit 0 и разобранный JSON.
3. **Классификация элементов rollup — белые списки, остальное «неизвестно».**
   `CheckRun`: статус `QUEUED|IN_PROGRESS|WAITING|PENDING|REQUESTED` —
   pending; `COMPLETED` + `SUCCESS|NEUTRAL|SKIPPED` — ок; `FAILURE|
   CANCELLED|TIMED_OUT|ACTION_REQUIRED|STARTUP_FAILURE|STALE` — красный.
   `StatusContext` (внешний CI): `SUCCESS` — ок; `PENDING|EXPECTED` —
   pending; `FAILURE|ERROR` — красный. Всё прочее (новое значение,
   неизвестный `__typename`, нет поля) — «неизвестно», и это застревание,
   а не «зелёный по умолчанию». Приоритет: красный > неизвестно > pending >
   зелёный.
4. **Критерий «CI не настроен» ошибается в сторону ожидания и не разбирает
   YAML.** Merge идёт без ожидания только когда выполнены оба условия:
   (а) в запушенной голове (по SHA, не по рабочему дереву) в
   `.github/workflows` нет ни одного файла `*.yml`/`*.yaml`, и (б) у PR на
   запушенной голове нет ни одной проверки. Файлы перечисляются
   `git ls-tree -z --name-only <SHA> -- .github/workflows/` (`-z` — пути не
   квотируются, не-ASCII имена читаются как есть); содержимое файлов не
   читается, триггеры (`on:`) не разбираются. Любой такой файл — «настроен»,
   независимо от триггеров: workflow только по `schedule`/`workflow_dispatch`
   тоже считается настроенным CI. Если файл есть, пустой список проверок —
   это «ещё не зарегистрировался»: опрос продолжается до окна появления
   (120 с, затем застревание «проверки не появились»). Если файлов нет, но
   проверки уже видны (внешний CI) — ждём их как обычно. Каталога нет или в
   нём нет `*.yml|*.yaml` (например, только `README.md`) и проверок нет —
   «не настроен». Сбой `git ls-tree` — застревание «не удалось определить»,
   не «не настроен».
   Почему не разбираем YAML workflow: самодельный разбор формата — повторяющийся
   класс дыр (кавычки и комментарии в `on:`, алиасы, flow-блоки, квотирование
   путей в выводе git; issue #201 — тот же класс в другом месте), и каждая
   дыра означает merge без CI. Единственный источник правды о триггерах
   ДО регистрации проверок на GitHub — сам файл, но цена его разбора выше
   выигрыша: ошибка разбора стоит merge без CI, а выигрыш — только workflow,
   которые никогда не запускаются на PR/push (расписание, ручной запуск).
   Цена принятого правила — лишнее ожидание окна появления (120 с) и
   застревание задачи для проекта, у которого есть только такие workflow;
   это fail-closed, человеку остаётся нажать merge. Ложное «настроен» стоит
   120 с и застревания, ложное «не настроен» — merge без CI, поэтому любая
   неоднозначность разрешается в «настроен».
5. **Голова проверяется.** Статус засчитывается, только если `headRefOid`
   равен SHA, который ralph запушил (`git rev-parse HEAD` после push):
   сразу после push GitHub может ещё отдавать прежнюю голову с её
   зелёными проверками. Несовпадение — «ещё не обновилось» (то же окно
   120 с, затем застревание). `gh pr merge` получает
   `--match-head-commit <SHA>` — если голова PR изменилась после
   проверки, merge отклоняется самим GitHub (и это застревание «merge не
   удался»).
6. **Зелёный засчитывается после двух опросов подряд.** Workflows одного
   push регистрируются не атомарно, а быстрые (секунды: `spec-annotation-
   check`, `version-bump-check`) могут успеть отчитаться до регистрации
   медленного `gates`. Два зелёных опроса через интервал закрывают это
   окно без знания, сколько проверок «должно» быть.
7. **Ожидание ограничено.** Верхняя граница — новый атрибут
   `policies.autopilot.budget.ci.maxMinutes` (дефолт 15; валидатор —
   общий `config_number`, ноль/нечисловое → предупреждение и дефолт, как у
   соседних бюджетов). Отдельный атрибут, а не бюджет задачи
   (`task.maxMinutes` — время headless-процесса `claude -p`, уже
   завершившегося; длительность CI — свойство CI проекта, не агента) и не
   остаток бюджета прогона (ADR-017 §2: остаток прогона не сокращает уже
   выбранную задачу). Интервал опроса 10 с и окно появления 120 с — не
   политика проекта, а константы; переопределяются env-швами
   `ADK_RALPH_CI_POLL_SECONDS`/`ADK_RALPH_CI_APPEAR_SECONDS`, чтобы
   фикстуры шли за секунды без реального времени.
8. **Стоп-файл и бюджет прогона внутри ожидания не проверяются.** ADR-018
   фиксирует единственную точку проверки стоп-файла — граница итерации
   («текущая итерация доигрывается»); ADR-017 §2 — то же для бюджета
   прогона. Ожидание CI — часть текущей итерации: оно ограничено
   `ci.maxMinutes`, значит превышение бюджета прогона/реакция на
   стоп-файл запаздывают не более чем на эту величину. Прерывание
   ожидания по стоп-файлу потребовало бы второй точки проверки и
   противоречило бы ADR-018.
9. **Fail-closed без новых исходов.** Красный CI, таймаут, «проверки не
   появились», чужая голова, неизвестное состояние, три подряд сбоя `gh`
   (то же «до 3 попыток», что ADR-019 §3), нераспознанный ответ — всё
   возвращает `STUCK <причина>` из `resolve_ready_pr`, дальше —
   существующий `mark_stuck` (needs-human, уведомление, `result=stuck`),
   прогон продолжается. Схема журнала (ADR-001) не меняется: новых
   значений `result` и полей нет, меняется только текст `reason`.

Отклонённые альтернативы:
- `gh pr checks --watch` — бесконечное ожидание и зависимость от кодов
  выхода, различающихся по версиям `gh` (см. п.2).
- «Проверки не появились за окно → CI не настроен → merge» — fail-open:
  задержка регистрации у GitHub превращалась бы в merge без CI.
- Решать «не настроен» по одному пустому списку без чтения workflow-файлов —
  ровно ложное «не настроен» сразу после push.
- Разбирать блок `on:` workflow-файлов (триггеры `push`/`pull_request`) —
  самодельный парсер YAML, источник дыр «merge без CI» (см. п.4).
- Прерывать ожидание стоп-файлом/бюджетом прогона (п.8).

## Последствия

- `adk-ralph.sh` не мержит актуализированную ветку, чей CI красный,
  не завершён или не удалось прочитать; застрявшая так задача уходит
  человеку с понятной причиной в сводке/журнале.
- Остаточные риски (не закрываются без знания о ветке-защите):
  внешний CI без workflow-файла, регистрирующийся после первого опроса,
  не будет замечен (реальная гарантия — required status checks в защите
  ветки, которые `gh pr merge` не обходит; issue #212 в ADR-008);
  workflow-файл есть, но не запускается на этот PR (расписание, ручной
  запуск, фильтр `paths`/`branches`/`tags`) — пустой список проверок при
  «настроенном» CI даёт застревание «проверки не появились» — осознанное
  направление отказа, человеку остаётся нажать merge.
- Ожидание идёт в подоболочке `$(...)`: Ctrl-C останавливает его сразу,
  SIGTERM доставляется обработчику после возврата из ожидания (тот же
  режим, что у локальных гейтов и `gh pr checkout`).
- Фикстуры `adk-ralph.sh`, доходящие до push актуализированной ветки,
  обязаны отвечать на `gh pr view --json headRefOid,statusCheckRollup`
  (тело — JSON с `headRefOid` равным HEAD ветки).
