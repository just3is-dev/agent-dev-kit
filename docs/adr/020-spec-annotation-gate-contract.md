# ADR-020: spec-annotation-check.sh — гейт в CI, номер issue из тела PR, а не из имени ветки

Дата: 2026-09-30
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #200 фиксирует петлю дефектов: критерий приёмки помечается в спеке
аннотацией `(ждёт #N)` (правило шага 3 `commands/work.md`), пока реализующий
issue #N не закрыт; PR, закрывающий issue #N, обязан снять аннотацию в том
же PR — «тест появился, «ждать» больше нечего». За одну веху это дважды
поймал ревьюер вручную (PR #198 — AC-4, PR #199 — AC-6): класс ошибки
стабильный, инструкция — самый слабый слой контроля, механическая проверка
дешевле повторного ручного вылавливания. Issue оставляет открытым главный
вопрос: где живёт логика (CI `.github/scripts/` рядом с гейтом бампа версии,
или локальный `scripts/check`) и как гейт узнаёт номер N — из тела PR
(`Closes #N`) или из имени ветки (конвенция `issue-N-*`).

## Решение

1. **Гейт — в CI (`.github/scripts/spec-annotation-check.sh` +
   `.github/workflows/spec-annotation-check.yml`), не в `scripts/check`.**
   Прямая аналогия с `version-bump-check.sh` (issue #151, ADR-013):
   единственный надёжный источник номера N — `Closes #N` в теле PR, а тело
   PR вне git-дерева — доступно только через `gh`/GitHub Actions контекст
   (`github.event.pull_request.body`), то есть требует сети. `scripts/check`
   — контракт кита (docs/contract.md) без сети и без внешних вызовов;
   протаскивать туда `gh api` ради одного гейта сломал бы это свойство для
   всех остальных проверок в том же прогоне.
2. **Номер N — из тела PR, не из имени ветки.** Отклонённая альтернатива —
   парсить `issue-N-*` из имени текущей ветки локально (без сети, быстрее).
   Отклонено: конвенция имени ветки — соглашение `commands/work.md`, не
   жёсткий контракт — ветка, заведённая вручную или через другой инструмент
   без суффикса `issue-N-*`, делает локальный вариант слепым молча (гейт
   промолчит там, где обязан был сработать) — то есть ровно тот тихий пропуск,
   который issue #200 пытается устранить. `Closes #N` — уже обязательное
   поле тела PR (шаг 5 `commands/work.md`, «Тело: Closes #N») — единственный
   из двух источников формально закреплённый конвенцией кита. CI-гейт платит
   за это сетью (тот же компромисс, что ADR-013 приняла для
   `version-bump-check.sh`, — там номер версии тоже нельзя было получить
   локально без чтения base-ветки).
3. **Скрипт ищет буквальную подстроку `(ждёт #N)` по всем
   `docs/specs/*.md`, не только по изменённым PR файлам.** Дефект, который
   ловит issue #200 (PR #198/#199), — забытая аннотация в спеке, которую
   PR вообще не трогал (реализующий тест добавлен, а строка критерия в
   спеке — нет), поэтому сравнение только списка изменённых путей (как у
   `version-bump-check.sh`, где именно список изменений — предмет проверки)
   здесь не годится: гейту нужно текущее состояние `docs/specs/` на голове
   PR, а не дифф. Соответственно вход скрипта проще, чем у
   `version-bump-check.sh`, — без diff и без сравнения base/head версий,
   только корень проекта и тело PR.
4. **Разбор тела PR («Closes #N») — внутри скрипта, не в workflow.**
   Отклонённая первая версия (круг 1 ревью PR #242) держала regex-разбор
   тела как inline-однострочник в `run:` шаге workflow — непокрытый
   фикстурами код, ловивший ложные совпадения (`discloses #5` матчился как
   `closes #5`) и не понимавший варианта `Closes: #200`. Перенос разбора в
   скрипт (тело PR на stdin, `project_root` единственным аргументом) даёт
   то же тестовое покрытие фикстурами `tests/run.sh`, что и остальная
   логика гейта — workflow остаётся тонкой обёрткой, которая только
   передаёт `github.event.pull_request.body` через переменную окружения.
   Разбор — регистронезависимый `closes[:]?\s*#N` с левой границей слова
   (не часть `[a-z]`), несколько `Closes #N` в одном теле — каждый номер
   проверяется независимо. Другие закрывающие глаголы GitHub (`Fixes`,
   `Resolves`, …) и кросс-репо ссылки (`owner/repo#N`) не разбираются —
   конвенция кита фиксирует ровно `Closes #N` в своём репозитории (см.
   «Последствия»).
5. **Сообщение отказа называет `commands/work.md, шаг 3` буквально и
   перечисляет файл(ы) спеки с оставшейся аннотацией** — тот же принцип
   прозрачного отказа, что `version-bump-check.sh` (называет
   `docs/contract.md`, раздел «Версионирование плагина»): человек, увидев
   красный CI, должен без раскопок понять, какое правило нарушено и где
   именно его починить.

Отклонённые альтернативы:
- Сравнение с base-версией спеки (аннотация была в base, исчезла в head) —
  отклонено: подход не ловит забытую аннотацию в файле, который PR вообще
  не менял (ровно случай PR #198/#199), а только различие внесённых правок.
- Один общий скрипт с `version-bump-check.sh` (два гейта в одном файле) —
  отклонено: разные по природе проверки (бамп версии vs аннотация спеки),
  разный вход (диапазон версий+пути vs корень+номера issue) — общий файл
  усложнил бы оба контракта без выигрыша, `release-check.sh` и
  `version-bump-check.sh` уже живут раздельно как прецедент «одна забота —
  один скрипт».

## Последствия

- Гейт применяется только к новым PR (событие `pull_request` после
  появления этого workflow) — уже смерженные PR с забытой аннотацией (если
  такие остались) не переоцениваются задним числом.
- Триггер — `types: [opened, edited, synchronize, reopened]`, не голый
  `pull_request` (круг 1 ревью PR #242): единственный вход гейта — тело
  PR, а дефолтные типы события (`opened`/`synchronize`/`reopened`) не
  включают правку описания уже открытого PR — без `edited` дописанный
  задним числом `Closes #N` или снятая по ошибке аннотация не
  перепроверялись бы до следующего push.
- PR, тело которого не содержит `Closes #N` (или использует другой
  закрывающий глагол — `Fixes`, `Resolves` — а не `Closes`, как предписывает
  шаг 5 `commands/work.md`), гейтом не проверяется вовсе — согласовано с
  DoD issue #200 («PR без Closes — гейт молчит»), но означает, что PR,
  отклонившийся от конвенции тела PR, тихо теряет и эту проверку тоже;
  отдельно не устраняется этой задачей.
- `docs/contract.md` не описывает этот гейт (в отличие от версии-бампа,
  зафиксированного в разделе «Версионирование плагина») — правило живёт в
  `commands/work.md` (шаг 3) и в самом гейте; расширять `docs/contract.md`
  под каждый CI-гейт кита не требуется, пока гейт не определяет что-то
  общее для всех проектов на ките (версии-бамп определяет).
