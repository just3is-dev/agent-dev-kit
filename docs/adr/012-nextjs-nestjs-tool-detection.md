# ADR-012: nextjs/nestjs — детект линтера и тест-раннера вместо хардкода

Дата: 2026-09-20
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #170: контрактные `templates/nextjs` и `templates/nestjs` были
написаны под eslint+jest (nestjs) / eslint+vitest (nextjs), но реальные
генераторы дрейфуют быстрее шаблона. Реальный прогон сегодняшних
генераторов (2026-09-20, из временных директорий вне репозитория):

- `npx create-next-app@latest --typescript --eslint --tailwind --app
  --src-dir --use-npm` (create-next-app 16.3.5): ставит **eslint** (`^9`,
  `eslint-config-next`), **не ставит вообще никакого тест-раннера** —
  ни jest, ни vitest не входят в devDependencies свежего проекта.
- `npx @nestjs/cli new --package-manager npm` (@nestjs/schematics
  12.0.3): ставит **oxlint** (`oxlint.json`, `"lint": "oxlint src/
  test/"`) и **vitest** (`vitest.config.ts`, `vitest.config.e2e.ts`,
  `@vitest/coverage-v8`) — ни eslint, ни jest в devDependencies нет.

Итог: старый шаблон nestjs (`npx eslint`, `npx jest`) звал бы инструменты,
которых в свежем nest-проекте физически нет — `npx` либо молча тянет их
транзитивно (не фиксируется в package.json, тянет лишние зависимости
и версии на свой выбор), либо, если офлайн/lockfile строгий, падает.
Старый шаблон nextjs уже был непоследователен в другую сторону:
`scripts/check` звал eslint (совпадает с генератором), но `scripts/test`
звал vitest, которого create-next-app не ставит — на практике команда
«работала» только потому что `npx vitest` транзитивно скачивал пакет
на лету, что и есть то самое «тянет лишние зависимости» из issue.

## Решение

Вариант (б) — детект вместо хардкода. `scripts/check` и `scripts/fix`
определяют линтер по `package.json` (`dependencies`/`devDependencies`):
`oxlint`, если он объявлен, иначе `eslint`; `scripts/test` — тест-раннер
тем же способом: `vitest`, если объявлен, иначе `jest`. Ни один из
ожидаемых инструментов не найден — скрипт падает с явным сообщением в
stderr (не тянет что-то через `npx` втихую и не пропускает шаг молча).

Отклонённые альтернативы:
- (а) просто переписать хардкод под сегодняшний вывод генераторов —
  решает проблему на сегодня, но это тот же класс дрейфа: следующее
  обновление `create-next-app`/`nest new` снова разъедет тулинг с
  шаблоном (тот же прецедент, что ac-check и swift-тесты issue #82 —
  гейт не должен предполагать конвенцию, которой в проекте может не
  быть).
- (в) комбинация — не нужна: чистый детект (б) уже покрывает оба
  шаблона без дополнительного слоя хардкода поверх.

Реализация — один и тот же inline-детект (`node -e` читает
`package.json`) в обоих шаблонах; не вынесен в общий файл: шаблоны
раскладываются по независимым проектам-потребителям (один проект берёт
ровно один шаблон), общего рантайма между `templates/nextjs` и
`templates/nestjs` нет — выносить два инлайна в общий файл ради
единственной пары копий добавило бы косвенность без потребителя.

Целостность whole-project lint для oxlint: `oxlint .` без `.gitignore`
(например, `nest new --skip-git` без `.gitignore`, или после ручного
удаления файла) обходит `node_modules` — в отличие от eslint, у
которого игнор node_modules встроен по умолчанию независимо от
`.gitignore`. Добавлен явный `--ignore-pattern node_modules` в
`oxlint`-ветку полного прогона, чтобы контракт не зависел от того,
успел ли уже появиться `.gitignore` с нужной записью на момент первого
`scripts/check`.

`commands/project-init.md` шаг 8 обновлён в ту же сторону: явно
называет пару признанных контрактом инструментов (eslint|oxlint,
vitest|jest) вместо голого «eslint» и «тест-раннер», и фиксирует
находку прогона — добавление `vitest` в проект без Vite (Next.js)
требует также `vite` как peer-зависимость (`vitest run` иначе падает
на старте `ERR_MODULE_NOT_FOUND: vite`), и что версия `@types/node`
генератора может конфликтовать с требованием vitest
(`--legacy-peer-deps` или апдейт `@types/node`) — воспроизведено
реальной установкой `npm install -D vitest` в свежий create-next-app
проект.

## Последствия

- Плюс: оба шаблона переживут следующий дрейф генератора без правки
  файлов кита — контракт подстраивается под фактический тулинг
  проекта, а не наоборот.
- Плюс: явная громкая ошибка вместо тихого «npx скачал что попало» или
  тихого пропуска — драйфующий случай (issue #170) при следующем
  дрейфе будет замечен на первом прогоне, а не спустя время.
- Минус/находка вне рамок issue: реальный прогон вскрыл отдельный,
  не связанный с этим issue баг — на свежем `nest new` (schematics
  12.0.3, `supertest@7.2.2`, `@types/supertest@7.2.1`) `tsc --noEmit`
  падает на `test/app.e2e-spec.ts` (`import { App } from
  'supertest/types'` не резолвится при `moduleResolution: nodenext` —
  ни `supertest`, ни `@types/supertest` не публикуют `exports`-карту
  для подпути `/types`). Это баг апстрима (несовместимость версий
  `@nestjs/schematics` и `supertest`/`@types/supertest`, отдельный
  от выбора линтера/тест-раннера), воспроизводится на чистом `nest new`
  без единого файла agent-dev-kit — не регрессия этого PR и не входит в
  его рамки. Изолированная проверка (временно убрать один этот импорт)
  подтверждает: остальной контракт (`tsc` по `src/`, `oxlint`, `vitest`)
  полностью зелёный — баг локализован именно в этом одном сгенерированном
  файле. Зафиксировано как отдельная находка, не как часть решения
  #170.
