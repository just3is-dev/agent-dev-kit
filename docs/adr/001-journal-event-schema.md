# ADR-001: схема событий журнала для агрегации /stats

Дата: 2026-08-07
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

SPEC-001 описывает журнал прогонов как append-only JSONL, по файлу на
единицу работы (`issue-<N>.jsonl`, `autopilot-<дата>.jsonl`), но не
фиксирует конкретные поля событий — это оставлено конкретным писателям
(issue #2 — запись из `/work`, issue #3 — запись из `/autopilot`).
Issue #4 (`/stats`, эта задача) зависит только от #1 (`adk-log.sh`,
универсальная запись `key=value`) и не блокирована #2/#3, но скрипту
агрегации нужна конкретная схема полей, чтобы считать круги ревью,
исходы и причины застреваний. Без зафиксированного контракта #2 и #3
могут задать несовместимые поля, и `/stats` не будет их понимать.

## Решение

Фиксируем схему событий, которую `adk-stats.sh` умеет агрегировать;
#2 и #3 обязаны писать события в этом формате через `adk-log.sh`.

`issue-<N>.jsonl` — по одной строке на событие задачи, в порядке:
- `event=start` — начало работы над задачей.
- `event=review round=<k> verdict=APPROVE|REQUEST_CHANGES` — одна
  строка на круг ревью.
- `event=outcome result=merged|stuck [reason=<текст>] [duration=<сек>] [diff=<строк>]` —
  финальный итог задачи; `reason` обязателен при `result=stuck`.
  `duration`/`diff` — поля из AC-1 SPEC-001 («длительность, размер
  диффа»), `adk-stats.sh` их пока не агрегирует (вне рамок AC-3), но
  #2 обязан их писать, чтобы не переопределять схему `outcome` заново
  при следующей задаче, которая их потребует. `result=merged` от
  `/work` фиксирует перевод PR в ready (сам `/work` не мержит —
  фактический merge позже делает человек или `/autopilot`).

`autopilot-<дата>.jsonl` — журнал одного прогона:
- `event=run_start`
- `event=task issue=<N> result=merged|stuck|skipped [reason=<текст>]` —
  одна строка на каждую обработанную в прогоне задачу; `reason`
  обязателен при `result=stuck`, как у `event=outcome` (дублирует факт
  из `issue-<N>.jsonl`, но не число кругов — не используется `/stats`
  для подсчёта задач, чтобы не задваивать с `issue-*.jsonl`).
- `event=run_end done=<k> stuck=<k> skipped=<k>`

`adk-stats.sh` источником «всего задач», кругов ревью, застреваний и
причин считает только `issue-*.jsonl` (файл = задача, 1:1). Поле
`timestamp` (служебное, ставит `adk-log.sh`) на событии `outcome`
(или последнем валидном событии файла, если `outcome` нет) — основа
для понедельной динамики. Круг ревью — `max(round)` среди событий
`review`, а не число строк `event=review`: append-only журнал не
гарантирует отсутствия повторной записи одного и того же круга (ретрай
записи, повторный вызов), а `max(round)` к дублю устойчив.

Задача без `event=outcome` (работа ещё не завершена) не считается
завершённой: не входит в «всего задач», среднее кругов и долю
застреваний — иначе `/stats`, вызванный во время активного `/work`,
искажал бы агрегаты сам по себе фактом своего существования.
`adk-stats.sh` показывает её отдельной строкой «в работе».

Отклонённые альтернативы (обоснование — см. «Решение» выше):
- Считать «всего задач» по `autopilot-*.jsonl` — отклонено.
- Включать незавершённые задачи (без `outcome`) в знаменатель — отклонено.
- Считать круги ревью числом строк `event=review` без учёта `round` —
  отклонено.

## Последствия

- #2 и #3 при реализации обязаны использовать эти имена событий/полей
  для журналирования из `/work` и `/autopilot`, иначе `/stats` будет
  показывать неполные или нулевые агрегаты для их записей.
- Схема событий — контракт между писателями журнала и `/stats`, а не
  требование самого `adk-log.sh` (он остаётся универсальным
  `key=value` механизмом без проверки полей).
- Расширение схемы новым полем — обратимо (старые строки без поля
  просто не участвуют в соответствующем агрегате). Смена имени
  существующего события/поля — новый ADR со ссылкой «supersedes».

## Расширения схемы

- 2026-08-14 (ADR-003, SPEC-002 AC-3): `event=task result=ready` и
  `event=run_end ... ready=<k>` в `autopilot-<дата>.jsonl` — PR готов,
  merge оставлен человеку.
- 2026-08-15 (issue #51, SPEC-002 AC-7): поле `type=<тип>` — тип задачи
  (имя типа из конфига `types.*`: `task`, `bug`, `fastFollow`,
  `consolidate`; источник — label issue, как в шаге 1 `/work`). Пишется
  `/work` в `event=start` и `event=outcome` (`issue-<N>.jsonl`) и
  `/autopilot` в `event=task` (`autopilot-<дата>.jsonl`). `adk-stats.sh`
  режет по нему агрегаты завершённых задач (количество и средние круги
  ревью на тип); тип задачи — последнее непустое значение поля среди
  событий файла, запись без поля (до этого расширения) считается `task`
  — прежние агрегаты не меняются.
- 2026-09-29 (issue #132, SPEC-003 AC-3/AC-6): поля расхода в
  `autopilot-<дата>.jsonl`. `event=task`: `duration=<сек>s` и
  `tokens=<n>` — фактический расход задачи; пишутся только когда
  `adk-ralph.sh` реально запускал headless-процесс этой итерацией
  (reused/skipped/blocked-on-ready — без них), `tokens` дополнительно
  опционален: usage читается из финального JSON `claude -p
  --output-format json`, и если процесс прерван по бюджету времени или
  вывод не разобрался, поле не пишется (минуты пишутся всегда), а
  токеновый бюджет задачи не применяется. **Состав счётчика `tokens`:
  input + output + cache_creation, БЕЗ cache_read** — cache_read на
  порядок больше остальных и отражает кэш-политику API, а не объём
  выполненной работы; бюджеты и калибровка по нему были бы шумом.
  `event=run_end`: `tokens=<сумма>` — расход прогона целиком (сумма по
  задачам с прочитанным usage). Записи прежних прогонов без этих полей
  легальны — читатели обязаны их пропускать.
- 2026-08-17 (issue #79, обещание SPEC-001): `/review` — третий писатель
  `issue-<N>.jsonl` (до этого только `/work`, #2). Логирует `event=review
  round=<k> verdict=...` тем же вызовом, что шаг 6 `/work`, продолжая
  нумерацию кругов задачи (`<k>` — `max(round)` среди уже записанных
  строк `event=review` + 1, а не отдельный счётчик с 1 — круги, начатые
  в `/work`, не задваиваются и не теряются). При переводе PR в ready
  после `APPROVE` добавляет `event=outcome result=merged` — сокращённая
  форма итога: только `result`, без `type`/`duration`/`diff`, которые
  обязан писать `/work` (`/review` не всегда запускается следом за
  `/work` в одном прогоне и не обязан знать длительность или тип
  задачи; полная форма для `/review` — расширение вне рамок issue #79).
  Повторная строка `event=outcome` в append-only журнале — не
  дублирование, а корректировка: `adk-stats.sh` берёт для итога
  последнюю встреченную строку `event=outcome` (см. «Решение» выше), так
  что задача, которую `/work` записал `stuck` после исчерпанных кругов,
  после `APPROVE` через `/review` агрегируется как `merged`. `<N>` не
  определён (PR без `Closes #N` и без ветки `issue-<N>-*`) — `/review`
  не логирует ни `event=review`, ни `event=outcome`: запись с неверным
  или пустым `<N>` исказила бы агрегаты фантомной задачей.
- 2026-08-26 (issue #139, SPEC-003 AC-1, ADR-007): `event=run_end
  reason=<текст>` в `autopilot-<дата>.jsonl` — причина остановки цикла,
  как её печатает сводка (SPEC-003 «Сводка прогона и HITL»: «пишется в
  журнал — `event=run_end` расширяется»). Первый писатель —
  `adk-ralph.sh`, со значением `"очередь пуста"` (штатная остановка) и
  четырьмя аварийными: `"gh issue list не удался"`, `"gh pr list не
  удался при разборе issue #N"`, `"внутренняя ошибка выбора задачи"` и
  `"claude -p завершился с ошибкой (exit <код>) при issue #N"` (все —
  ADR-007 §2-§4; список обязан оставаться синхронным между ADR-007,
  кодом `adk-ralph.sh` и этой записью — расхождение уже случалось, круг
  2 ревью PR #141). Будущие бюджет/breaker/стоп-файл (issues #130-135) —
  тем же полем, другими значениями. `/autopilot` это поле пока не пишет
  (его `event=run_end` без причины — цикл интерактивной сессии не
  завершается автономно по этим правилам).
- 2026-09-27 (issue #147, ADR-014): три аддитивных поля в
  `autopilot-<дата>.jsonl`, все — только `adk-ralph.sh`. (1) Поле
  `reused=true` на `event=task result=ready` — issue уже имел открытый
  ready-PR ДО запуска `claude -p` в этом прогоне (предстартовая проверка
  `find_pr_state`, ADR-014 §1): `claude -p` не вызывался вовсе, в отличие
  от обычного `result=ready` без этого поля (PR стал ready в результате
  реального исполнения этим прогоном). (2) Новое значение `result=
  blocked-on-ready` на `event=task` — задача, у которой ВСЕ открытые
  блокеры стали `ready` этим же прогоном, но сами ещё не смерджены (ADR-014
  §2): не
  `stuck`, не `skipped`, не кандидат, но и не пропадает из журнала молча,
  как раньше. Не входит в знаменатель `maxSkippedShare` (issue #134) —
  семантически не неудача. (3) Поле `blocked_on_ready=<k>` на
  `event=run_end` — число задач в этом состоянии за прогон, симметрично
  `ready=<k>`/`stuck=<k>`/`skipped=<k>`. Шестое значение
  `event=run_end.reason` — `"доступных задач нет: остались только задачи,
  заблокированные ready-PR блокера"` (реестр ADR-007 §3 обновлён синхронно).
  `adk-stats.sh` эти поля не агрегирует (агрегирует только
  `issue-*.jsonl`, не `autopilot-*.jsonl` — см. «Решение» выше).
- 2026-09-27 (issue #135, ADR-015): седьмое-девятое значения
  `event=run_end.reason` в `autopilot-<дата>.jsonl`, все — только
  `adk-ralph.sh`: `"системный breaker: красные гейты main"`, `"системный
  breaker: отказ записи журнала"`, `"системный breaker: серия конфликтов
  актуализации"` — breaker уровня системы (SPEC-003 «Стадийный circuit
  breaker», половина AC-5; вторая половина, уровень прогона —
  `maxStuckPerRun`/`maxSkippedShare`, issue #134 — ещё не реализована).
  Реестр ADR-007 §3 обновлён синхронно.
- 2026-09-27 (issue #134, ADR-016): десятое-одиннадцатое значения
  `event=run_end.reason`, тоже только `adk-ralph.sh`: `"breaker:
  застревания за прогон"` (накопленные `result=stuck` за прогон достигли
  `policies.autopilot.breaker.maxStuckPerRun`) и `"breaker: доля
  пропущенных за прогон"` (доля `result=skipped` от суммы
  `ready+stuck+skipped` выше `policies.autopilot.breaker.maxSkippedShare`,
  при знаменателе не ниже 4) — breaker уровня прогона, вторая половина
  AC-5 (первая — уровень системы, issue #135 выше). Никаких новых полей
  на `event=run_end` сверх `reason`: `ready`/`stuck`/`skipped` уже
  считаются существующими счётчиками. Реестр ADR-007 §3 обновлён
  синхронно.
- 2026-09-27 (issue #131, ADR-017): двенадцатое-тринадцатое значения
  `event=run_end.reason`, тоже только `adk-ralph.sh`: `"бюджет прогона по
  времени"` — SPEC-003 «Жёсткие бюджеты», временная половина AC-3: бюджет
  `policies.autopilot.budget.run.maxMinutes` исчерпан на границе выбора
  следующей задачи — чистая остановка, текущая задача доведена до
  вердикта; и `"бюджет задачи по времени: рабочее дерево не чисто после
  прерывания issue #N"` — процесс `claude -p`, прерванный по бюджету
  задачи ПОСРЕДИ работы, мог оставить незакоммиченные правки, которые
  `return_to_default_branch` (issue #144) молча перенесла бы на default
  branch; вместо продолжения прогон останавливается целиком (ADR-017 §4).
  Заодно новое значение `result=stuck reason="бюджет задачи по времени"`
  на `event=task` (бюджет `policies.autopilot.budget.task.maxMinutes`
  исчерпан, `claude -p` прерван) — та же свободнотекстовая форма поля
  `reason`, что уже используют «PR остался черновиком»/«PR не создан»
  (ADR-007 §2-3), отдельного реестра для причин `event=task` в ките нет.
  Пишется независимо от того, осталось ли рабочее дерево чистым после
  прерывания — см. уточнение записи 2026-09-28 ниже: круг 2 ревью PR #193
  сделал этот путь обязательным и на грязном дереве, а не только на чистом.
  Реестр ADR-007 §3 обновлён синхронно; заодно зафиксирован
  пре-существующий (до issue #131) пробел этого реестра — значение issue
  #144 «не удалось вернуть дерево…» в него исторически не попало, бэкфилл
  вне рамок этой задачи.
- 2026-09-28 (issue #131, ADR-017 §1, круг 4 ревью PR #193): четырнадцатое
  значение `event=run_end.reason` в `autopilot-<дата>.jsonl` —
  `"прерван сигналом <SIG>"` (`SIG` — `INT`/`TERM`) — обработчик сигнала
  самому `adk-ralph.sh` (`ralph_signal_cleanup`), не связан с бюджетами;
  писавшееся кодом уже с круга 1 ревью PR #193, но обнаруженное не
  внесённым в реестр только этим кругом (мутационное тестирование). Заодно
  исправление: поле `done` на этом событии отражает фактическое число
  смерженных этим прогоном до сигнала (`merged_count`, issue #129), не
  безусловный литеральный `0` — до этого круга ревью обработчик писал `0`
  независимо от факта merge, расхождение найдено тем же мутационным
  тестированием. Уточнение записи от 2026-09-27 выше: `result=stuck
  reason="бюджет задачи по времени"` на `event=task` пишется независимо от
  чистоты рабочего дерева после прерывания (грязное дерево не пропускает
  этот путь, ADR-017 §4) — прежняя формулировка ошибочно описывала «дерево
  осталось чистым» как единственный случай. Реестр ADR-007 §3 обновлён
  синхронно.
