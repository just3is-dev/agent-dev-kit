# ADR-009: спека мержится вместе с аннотациями `/plan`, не сразу после апрува

Дата: 2026-09-14
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

`/spec` инструктировал мержить approved-спеку в main сразу после апрува
пользователя. Единственный механизм, который снимает с `ac-check`
требование покрытия для критерия, чей тест ещё не написан, — аннотация
`AC-N (ждёт #<issue>)` — по построению может появиться только в `/plan`:
issues создаются после декомпозиции и апрува плана, аннотация проставляется
следом. `/plan` заведомо запускается позже, чем `/spec` мержит спеку.

В промежутке между этими двумя командами approved-спека в main не имеет
ни тестов, ни аннотаций — `ac-check` (корректно, по своему контракту)
красный, и гейт блокирует любой merge в проекте, пока кто-нибудь не
запустит `/plan`. Это институциональный дедлок: команды `/spec` и `/plan`
противоречат друг другу по порядку, а не ac-check.sh ошибается (issue
#172). В самом ките баг ни разу не проявился только из-за независимого
дефекта #171 (коллизия номеров AC между спеками маскировала непокрытые
критерии предыдущими тегами) — фикс #171 обнажает окно и здесь.

## Решение

Approved-статус спека получает **в своей ветке** (`spec/NNN-<слаг>`), PR
спеки при этом остаётся черновиком — `/spec` больше не мержит его сам.
`/plan` при запуске определяет, находится ли спека ещё в открытой ветке
(её PR не смержен) или уже в main:

- **ветка спеки открыта** — `/plan` переключается на неё
  (`git checkout spec/NNN-<слаг>`) и работает по спеке оттуда, не из main.
  После апрува плана, создания issues и расстановки аннотаций
  `AC-N (ждёт #N)` эта правка коммитится в ту же ветку; `/plan` сам
  переводит PR спеки в ready и мержит его (squash) финальным шагом.
  Спека и аннотации попадают в main одним коммитом — промежуточного
  состояния «approved-спека без покрытия и без аннотаций уже в main» не
  существует по построению. Merge делает сам агент, без дополнительного
  ревью-гейта: пользователь уже одобрил и спеку (шаг 4 `/spec`), и план
  (до создания issues) — это тот же принцип, что и у исходного
  прямого merge в `/spec`, ревью-агент в цикле спека → план не участвует.
- **ветка спеки уже смержена или не существует** — обратная
  совместимость со спеками, approved-статус которых был проставлен до
  этого решения (или смерженными вручную): `/plan` работает как раньше,
  от main, а аннотации коммитятся обычным PR. Для таких спек риска нет —
  main уже был зелёным в момент их merge, окно issue #172 сюда не
  относится ретроактивно.

Отклонённые альтернативы:
- Промежуточный статус спеки (`approved-pending-plan` и т.п.) — отклонено:
  лишняя семантика статуса ради обхода порядка команд, `ac-check.sh`
  пришлось бы отдельно учить новому статусу, хотя проблема — в порядке
  вызова команд, а не в состояниях спеки.
- Пропускать в `ac-check` approved-спеки без единого покрытого критерия —
  отклонено (уже рассматривалось и отклонено в теле issue #172): дыра —
  спека, для которой `/plan` никогда не запустят, никогда не станет
  красной, хотя формально не покрыта ничем.

## Последствия

- `/spec` больше не мержит PR спеки самостоятельно — эта ответственность
  переходит к `/plan` (финальный шаг после создания issues).
- Approved-спека, чей `/plan` ещё не запускали, — легальное и потенциально
  долгоживущее состояние в СВОЕЙ ветке. Это не то же самое, что «`ac-check`
  её не видит»: CI гоняет `ac-check` на каждом PR (`.github/workflows/ci.yml`,
  `templates/*/scripts/check`), поэтому сама ветка спеки корректно
  показывает красный `ac-check`, пока в ней approved-статус уже есть, а
  аннотаций ещё нет, — это ожидаемое состояние незавершённого draft-PR,
  как и падающие тесты в разгар любой другой задачи. Важно другое: эта
  краснота никогда не достигает main, потому что PR спеки не переводится
  в ready и не мержится, пока не готовы аннотации, — а значит не может
  заблокировать CI ни одного чужого PR в репозитории (в отличие от старого
  порядка, где approved-спека без аннотаций сама оказывалась в main и
  красила `ac-check` там, блокируя любой merge в проекте). Фикс не прячет
  красноту, а не даёт ей покинуть черновик.
- `/plan` обязан уметь определять режим (ветка спеки vs main) и работать
  в обоих — переключение на ветку стало первым шагом команды.
- Существующие approved-спеки, уже находящиеся в main на момент этого
  решения, не мигрируются: для них `/plan` продолжает работать по старому
  пути (аннотация обычным PR, без merge спеки).
- Issue #171 (коллизия номеров AC между спеками) остаётся отдельной
  задачей — это решение не трогает `hooks/scripts/ac-check.sh`.
