# ADR-007: adk-ralph.sh — выбор задачи без milestone, поиск PR по префиксу ветки, event=run_end.reason

Дата: 2026-08-26
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #139 (SPEC-003, docs/specs/003-autonomy.md) вводит `adk-ralph.sh` —
bash-скрипт, повторяющий цикл `/autopilot` (шаг 1 `commands/autopilot.md`)
как headless-процесс без интерактивной LLM-сессии. Три места, где
буквальное повторение правила `/autopilot` невозможно или недостаточно,
потребовали отдельного решения:

1. `/autopilot` сужает очередь issues «текущим milestone» — решение,
   которое в интерактивной сессии принимает модель, читая контекст
   разговора. У `adk-ralph.sh` такого суждения нет: скрипт не получает
   номер/название milestone ни аргументом, ни конфигом.
2. `/autopilot`/`/work` разбирают исход задачи по фактам `gh`, но не
   фиксируют конкретный запрос для «найти PR, отвечающий issue #N» —
   в интерактивной сессии это делает модель произвольным способом.
3. Схема журнала ADR-001 не даёт `event=run_end` поля для причины
   остановки цикла, а SPEC-003 явно ожидает её и в сводке, и в журнале
   («пишется в журнал — event=run_end расширяется»).
4. `adk-ralph.sh` выполняет саму задачу внешним headless-процессом
   `claude -p` — сбой этого процесса (бинарь не установлен, не
   авторизован, упёрся в лимит, разово споткнулся) неотличим от «модель
   отработала и не создала PR», если проверять только исход
   `find_pr_state` после вызова (круг 3 ревью PR #141): без отдельной
   проверки каждая итерация очереди дошла бы до ложного «PR не создан» и
   получила бы липкую метку `needs-human`.

## Решение

1. **Без milestone-фильтра.** `adk-ralph.sh` берёт очередь как «все
   открытые issues репозитория» (`gh issue list --state open`), применяя
   только два условия шага 1 `/autopilot`: без `needs-human`, все
   `Blocked by #N` закрыты. Отклонённая альтернатива — параметр
   `--milestone`/конфиг «текущий milestone»: отложено, у SPEC-003 нет
   такого требования, а любой milestone в этом ките и так создаётся
   только из утверждённого плана (ворота спеки/плана не делегируются),
   поэтому смешение milestone'ей не нарушает инвариант «ralph работает
   только по issues из утверждённого плана» — просто ослабляет
   независимость параллельных вех друг от друга. Если это станет
   проблемой на практике — отдельная задача добавит фильтр не меняя
   остальной цикл.
2. **Поиск PR — по префиксу имени ветки.** Ветка задачи — `issue-<N>-*`
   (шаг 2 `commands/work.md`), поэтому вместо полнотекстового поиска
   `Closes #N` (`gh search`, индекс может отставать, и хуже
   воспроизводится стабом в тестах) `adk-ralph.sh` берёт
   `gh pr list --state open --json number,isDraft,headRefName` и находит
   PR, чей `headRefName` начинается с `issue-<N>-` (дефис — обязательная
   граница префикса, иначе `issue-1-` ложно совпал бы с `issue-13-...`).
   Несколько совпадений (повторные попытки) — берётся PR с наибольшим
   номером.
3. **`event=run_end reason=<текст>`** — новое поле, аддитивное расширение
   ADR-001 (как и `result=ready` в ADR-003). Штатное значение —
   `"очередь пуста"`; аварийные — `"gh issue list не удался"`, `"gh pr
   list не удался при разборе issue #N"` (факты о PR не удалось получить
   — не выдавать это за «PR не создан», не штамповать `needs-human`
   вслепую), `"внутренняя ошибка выбора задачи"` (защитная ветка на
   случай, если `select_next` вернёт не то, что ожидает вызывающий
   bash-код) и `"claude -p завершился с ошибкой (exit <код>) при issue
   #N"` (п.4 выше). Ни одно из пяти не закрывает список — бюджеты/
   breaker/стоп-файл (issues #130-135) допишут туда свои значения тем же
   полем. Все пять значений обязаны совпадать между этим файлом,
   `adk-ralph.sh` и реестром ADR-001 «Расширения схемы» — расхождение
   уже случалось (круг 2 ревью PR #141) и правится синхронной правкой
   всех трёх мест, а не только кода.
4. **Префлайт + проверка exit-кода headless-процесса.** Перед циклом —
   `command -v claude` рядом с проверкой наличия `work.md`: тот же класс
   отказа старта без единого побочного эффекта (журнал ещё не начат), что
   и отсутствие конфига/файла инструкций. Внутри цикла — ненулевой exit
   `claude -p` останавливает прогон целиком через `event=run_end
   reason="claude -p завершился с ошибкой…"` (п.3), не доходя до
   `find_pr_state`: тот же принцип различения «отсутствие фактов ≠ факт
   отсутствия», что и в п.2/п.3 для сбоя `gh pr list`. Остановка всего
   прогона (не просто `result=stuck` для одной задачи) — потому что
   причина сбоя (не установлен/не авторизован/лимит) как правило не
   специфична для конкретного issue и повторится на следующей итерации
   тем же образом; выборочный `needs-human` по одной задаче замаскировал
   бы системную проблему под серию несвязанных отказов задач.
5. **Fail-closed на неизвестное значение `policies.autopilot.enabled`.**
   Значение вне `{"true","false"}` (опечатка в значении, не отсутствие
   атрибута/файла — за это `lib/config.sh` отвечает своим `exit 0` и
   дефолтом `"true"`) — отказ старта без единого побочного эффекта, той
   же дисциплиной, что и остальное чтение конфига `adk-ralph.sh` (issue
   #129). Отличается от `enabled=false` только текстом сообщения; оба
   пути завершаются до `run_start`, поэтому в журнале не остаётся
   сиротской записи без `run_end`.

## Последствия

- Проект с несколькими одновременно открытыми milestone (незакрытая веха
  A + свежепринятая веха B) получит от `adk-ralph.sh` единый интерлив
  задач A и B за один прогон — не то же самое, что `/autopilot`
  (сужает список сам). Если понадобится изоляция по вехе — новый
  параметр, не поведение по умолчанию.
- Ветка задачи обязана называться `issue-<N>-*` (уже требование
  `commands/work.md`) — иначе `adk-ralph.sh` не найдёт PR и посчитает
  задачу застрявшей («PR не создан»), даже если PR существует под другим
  именем ветки.
- Читатели `autopilot-<дата>.jsonl` не должны считать набор полей
  `event=run_end` закрытым — `reason` может появляться и не появляться
  в зависимости от того, какая причина остановки сработала.
- Окружение, где выполняется `adk-ralph.sh`, обязано иметь установленный
  и авторизованный бинарь `claude` в `PATH` — иначе прогон не стартует
  (префлайт) либо останавливается на первой же задаче (сбой в цикле), но
  не тратит остальную очередь на ложные `needs-human`.
- Issue уже с меткой `needs-human` (выставленной прошлым прогоном или
  человеком) не в очереди этого прогона: если такой issue блокирует
  другую задачу, зависимая задача пропускается каскадом (её блокер не
  решён), но сам уже-`needs-human`-issue не логируется как
  `result=skipped` — иначе счётчик пропущенных завышался бы задачами,
  которые никогда не были бы взяты в этот прогон.
