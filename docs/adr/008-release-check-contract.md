# ADR-008: release-check.sh — контракт вывода, поиск предыдущего тега, формат notes

Дата: 2026-09-06
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #155 (SPEC-004, docs/specs/004-plugin-versioning.md, AC-2) вводит
релизный процесс из истории main без рукописного CHANGELOG:
`.github/scripts/release-check.sh` решает, нужен ли релиз по текущему
HEAD, а `.github/workflows/release.yml` — тонкая обёртка, которая по его
вердикту ставит git-тег и создаёт GitHub Release. Три вещи не заданы
issue буквально и требуют решения: как скрипт сообщает вердикт workflow
(текстовый вывод — единственный канал между ними), как искать
«предыдущий тег» для диапазона notes, и в каком формате отдавать сами
notes.

## Решение

1. **Контракт вывода — три строки, а не машиночитаемый формат.**
   Нет релиза → одна строка `релиза нет: <причина>` (version не менялась /
   тег уже существует), exit 0. Есть релиз → `RELEASE\n<vX.Y.Z>\n<notes>`,
   exit 0. Отклонённая альтернатива — JSON на stdout (пара `jq` вызовов в
   workflow): для двух полей (тег + многострочные notes) считанный `sed
   -n Np` проще, чем тянуть в CI ещё один инструмент разбора, а `notes`
   всё равно идёт в GitHub Actions `GITHUB_OUTPUT` через delimiter-паттерн
   `notes<<EOF`, который сам по себе текстовый. Реальная ошибка (репозиторий
   не найден, `version` не читается) — exit 1 и сообщение в stderr, не
   вплетается в тот же трёхстрочный контракт.
2. **«Предыдущий тег» — `git describe --tags --abbrev=0 HEAD`.**
   HEAD на момент вызова скрипта ещё не тегирован (тег создаёт следующий
   шаг workflow), поэтому `describe` от HEAD находит ближайший тег среди
   предков, не including HEAD сам. Отклонённая альтернатива — `git tag
   --sort=-v:refname | head -1` (сортировка по семверу тегов): совпадает
   с `describe` только при линейной истории релизов без ручных тегов не по
   порядку коммитов; `describe` привязан к графу коммитов, а не к
   лексикографии версий, что и нужно для «коммиты между предыдущим
   релизом и этим». Тегов ещё нет вовсе (issue #156, первый релиз) —
   `describe` возвращает пусто, диапазон notes становится «вся история до
   HEAD» без отдельной ветки кода.
3. **Изменение version — сравнение HEAD против HEAD^, не против
   предыдущего тега.** Буквально по формулировке issue («изменилась ли
   version… относительно предыдущего коммита»). При squash-merge (метод
   приземления по умолчанию, docs/config.md) каждый push в main — один
   новый коммит, поэтому HEAD^ и есть «состояние main до этого PR»; сверка
   с предыдущим тегом дала бы то же самое в штатном случае, но
   маскировала бы повторный запуск workflow на том же HEAD после уже
   свершившегося релиза (тег есть, но commit тот же) — сценарий (в) DoD
   ловится отдельной проверкой существования тега, а не этой сверкой.
4. **Notes — `git log --format='- %s' <диапазон>`, порядок как у `git
   log` (новые сверху).** Заголовки коммитов — уже сообщения squash-PR по
   конвенции «глагол + результат (#N)» (SPEC-002), почему CHANGELOG не
   заводится отдельно (SPEC-004 «Релизы из истории»); `- ` — минимальное
   форматирование под markdown-тело GitHub Release, без склейки, авторов
   или дат, которые issue не просит.
5. **Скрипт не создаёт тег сам.** `git tag` + `gh release create` —
   в `release.yml`, после того как шаг с `release-check.sh` записал
   `should_release`/`tag`/`notes` в `GITHUB_OUTPUT`. Разделение по issue
   («тонкая обёртка») и по тестируемости: три DoD-сценария (а/б/в)
   проверяют чистую функцию скрипта на временных репозиториях
   (`tests/run.sh`, `git_c`) без сети и без реального создания тегов/
   релизов — ничего в `release.yml` не покрыто прогоном `claude`/`gh` по
   политике задачи (см. предупреждение issue: workflow не запускается
   вживую, только код и тесты).

## Последствия

- Любой будущий потребитель вывода `release-check.sh` (например, ручной
  вызов для дебага) обязан парсить построчно (`sed -n Np`), а не ожидать
  JSON — смена контракта на структурированный формат потребует правки и
  скрипта, и `release.yml`, и тестов одновременно.
- `release-check.sh` предполагает `fetch-depth: 0` при чекауте (полная
  история) — с мелкой историей `git describe`/диапазон `git log` дают
  неполные или ошибочные notes без явной ошибки скрипта. `release.yml`
  уже задаёт `fetch-depth: 0`; отдельный проект, подключающий этот
  паттерн, обязан сделать то же.
- Первый релиз по политике SPEC-004 (issue #156, AC-6) отработает тем же
  скриптом без отдельного кода — «нет тегов» уже обрабатывается веткой
  п.2, а не специальным флагом «это первый релиз».
