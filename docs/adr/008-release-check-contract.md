# ADR-008: release-check.sh — контракт вывода, поиск предыдущего тега, формат notes

Дата: 2026-09-06
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #155 (SPEC-004, docs/specs/004-plugin-versioning.md, AC-2) вводит
релизный процесс из истории main без рукописного CHANGELOG:
`.github/scripts/release-check.sh` решает, нужен ли релиз по текущему
HEAD, а `.github/workflows/release.yml` — тонкая обёртка, которая по его
вердикту ставит git-тег и создаёт GitHub Release. Несколько вещей не
заданы issue буквально и требуют решения: как скрипт сообщает вердикт
workflow (текстовый вывод — единственный канал между ними), как искать
«предыдущий тег» для диапазона notes, в каком формате отдавать сами
notes, и чем проверять валидность YAML самого workflow — в ките нет ни
одной такой проверки до этой задачи.

## Решение

1. **Контракт вывода — три строки, а не машиночитаемый формат.**
   Нет релиза → одна строка `релиза нет: <причина>` (version не менялась /
   тег уже существует), exit 0. Есть релиз → `RELEASE\n<vX.Y.Z>\n<notes>`,
   exit 0. Отклонённая альтернатива — JSON на stdout: для двух полей (тег +
   многострочные notes) `sed -n Np` в workflow проще, чем тянуть `jq`, а
   `notes` всё равно уходит в `GITHUB_OUTPUT` через текстовый
   delimiter-паттерн `notes<<EOF`. Реальная ошибка (репозиторий не найден,
   `version` не читается) — exit 1 и сообщение в stderr, отдельно от этого
   контракта. Разбор контракта в `release.yml` (`sed -n 1p`/`2p`/`tail -n
   +3`) прогоняется тестами на реальном stdout скрипта (сценарии а и б,
   `tests/run.sh`) — не только пишущая сторона.
2. **«Предыдущий тег» — `git describe --tags --abbrev=0 HEAD`.**
   Работает по графу коммитов (ближайший тег среди предков — включая сам
   HEAD, если он уже помечен), а не по лексикографии версий, что и нужно
   для «коммиты между предыдущим релизом и этим»; отклонённая
   альтернатива — `git tag --sort=-v:refname | head -1` совпала бы только
   при линейной истории тегов без ручных исключений. Тегов ещё нет вовсе
   (issue #156, первый релиз) — `describe` возвращает пусто, диапазон
   notes становится «вся история до HEAD» без отдельной ветки кода.
   Ограничение: если на HEAD случайно уже висит чужой (не целевой) тег,
   `describe` вернёт его, а не более раннюю метку — диапазон схлопнется и
   notes выйдут пустыми. На main этого кита ручных тегов, кроме
   релизных, не бывает; риск отмечен как известное ограничение, не как
   покрытый тестами случай.
3. **Изменение version — сравнение HEAD против HEAD^, не против
   предыдущего тега.** Буквально по формулировке issue («изменилась ли
   version… относительно предыдущего коммита»); отдельная проверка
   существования целевого тега (шаг перед формированием notes) уже ловит
   сценарий (в) DoD — повторный запуск workflow на том же HEAD после
   состоявшегося релиза.
4. **Notes — `git log --format='- %s' <диапазон>`, порядок как у `git
   log` (новые сверху).** Заголовки коммитов — уже сообщения squash-PR по
   конвенции «глагол + результат (#N)» (SPEC-002), это и есть причина, по
   которой CHANGELOG не заводится отдельно (SPEC-004 «Релизы из истории»).
5. **Скрипт не создаёт тег сам** — `git tag`/`git push`/`gh release
   create` целиком в `release.yml`, по issue («тонкая обёртка») и по
   тестируемости: сценарии (а/б/в) проверяют чистую функцию скрипта на
   временных репозиториях (`git_c`, `tests/run.sh`) без сети и без
   реального создания тегов/релизов, как и требует задача.
6. **Валидность YAML — `ruby -ryaml`, не PyYAML.** Кит стандартизован на
   bash + python3 (JSON везде — `hooks/scripts/*`, `scripts/check`), но
   YAML не в стандартной библиотеке ни того, ни другого; добавлять
   PyYAML как pip-зависимость под одну проверку — новая зависимость ради
   теста (project_vte_no_extra_deps — тот же принцип «сначала
   built-in»). Ruby с модулем `yaml` (Psych) — часть заводской установки
   и macOS (среда разработки), и образов `ubuntu-latest`
   (`actions/runner-images`), то есть уже доступен без единой строчки
   установки. В отличие от `claude` в `scripts/check` (мягкая деградация
   `if command -v claude`, потому что валидация плагина — необязательный
   бонус), проверка YAML — обязательный DoD-сценарий: отсутствие ruby в
   среде — громкая ошибка теста, а не тихий пропуск, тем же принципом,
   что и обязательный `xcodegen` для `project.yml` в шаблоне swift-ios
   (issue #70) — инструмент, без которого нечего проверять, тестовый
   сценарий не притворяется прошедшим.
7. **Workflow запускается на push в main независимо от статуса CI того
   же коммита.** DoD не требует ждать зелёный CI перед релизом, а main и
   так защищён гейтами на уровне PR (ветка попадает в main, только
   пройдя `./scripts/check`/`./scripts/test` в CI); отдельный `needs`/
   `workflow_run`-триггер, ждущий job CI, — усложнение без обязывающего
   требования, отложено до появления реальной необходимости.

## Последствия

- Любой будущий потребитель вывода `release-check.sh` обязан парсить
  построчно, а не ожидать JSON — смена контракта на структурированный
  формат потребует правки и скрипта, и `release.yml`, и тестов
  одновременно.
- `release-check.sh` предполагает `fetch-depth: 0` при чекауте (полная
  история) — с мелкой историей `git describe`/диапазон `git log` дают
  неполные или ошибочные notes без явной ошибки скрипта. `release.yml`
  уже задаёт `fetch-depth: 0`; отдельный проект, подключающий этот
  паттерн, обязан сделать то же.
- Первый релиз по политике SPEC-004 (issue #156, AC-6) отработает тем же
  скриптом без отдельного кода — «нет тегов» уже обрабатывается веткой
  п.2, а не специальным флагом «это первый релиз».
- `./scripts/test` требует `ruby` в среде выполнения (дев-машина,
  CI-раннер) наравне с уже требуемым `python3` — отсутствие ruby красит
  гейт, а не пропускает проверку YAML молча.
- Ручной тег на текущем HEAD main (вне релизного процесса) сломает поиск
  «предыдущего тега» для следующего релиза (п.2, ограничение) — такая
  практика на main кита не принята и не должна появиться в обход
  `release.yml`.
