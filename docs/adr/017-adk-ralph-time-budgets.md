# ADR-017: adk-ralph.sh — бюджеты времени на задачу и на прогон

Дата: 2026-09-27
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

SPEC-003 «Жёсткие бюджеты» (AC-3, issue #131 — только временная половина;
токеновый бюджет — issue #132, множитель `size:large` — issue #133, обе
вне рамок этой задачи) требует: превышение бюджета времени на задачу
прерывает headless-процесс `claude -p` и застревает саму задачу
(`needs-human`, `result=stuck`), не останавливая прогон; превышение
бюджета прогона — чистая остановка цикла (текущая задача доводится до
вердикта, новая не начинается). Шесть решений не очевидны из текста issue
(четвёртое, пятое и шестое — находки круга 1/2 ревью PR #193, не исходного
текста issue, но того же класса неочевидности):

1. Чем измерять и прерывать время итерации в bash — внешним `timeout`/
   `gtimeout` или собственным опросом.
2. Как трактовать «остаток бюджета прогона меньше бюджета задачи».
3. Ноль/отрицательное значение атрибута бюджета в конфиге — ошибка
   конфига (дефолт с предупреждением) или осмысленное «без лимита».
4. Что делать, если прерванный ПОСРЕДИ работы `claude -p` (в отличие от
   штатного застревания, где процесс завершился сам) оставил рабочее
   дерево грязным — продолжать цикл как при любом другом `result=stuck`
   или это особый случай, и в каком порядке относительно обычного
   stuck-пути (needs-human/уведомление/`event=task`).
5. Job control (`set -m`), нужный для group-kill по бюджету задачи, —
   включать на весь скрипт или только вокруг самого фонового запуска
   `claude -p`.
6. Куда встраивается проверка бюджета прогона на границе итерации
   относительно стоп-файла (issue #130) и системного breaker'а красных
   гейтов main (issue #135) — рёбейз PR #193 поверх обоих потребовал
   явного порядка при их коллизии.

## Решение

1. **Измерение и прерывание — bash `$SECONDS` + фоновый процесс +
   `kill`, без `timeout`/`gtimeout`.** На машине, где ведётся разработка
   этого кита (macOS, дневная дообработка руками), не установлен ни
   `timeout` (GNU coreutils), ни `gtimeout` (тот же бинарь из
   `brew install coreutils`) — только `.github/workflows/ci.yml`
   (`ubuntu-latest`) имеет GNU `timeout` из коробки. Полагаться на внешний
   бинарь означало бы либо разное поведение теста локально и в CI (тест
   красный на машине разработчика), либо всё равно писать собственный
   fallback на случай отсутствия обеих команд — а если fallback обязателен
   в любом случае, экономнее иметь один канонический механизм, а не два
   (внешняя команда + запасной вариант), которые придётся поддерживать и
   тестировать порознь. `claude -p "$prompt"` запускается в подпроцессе
   (`(cd "$root" || exit 1; exec claude -p "$prompt") &`, `exec` — чтобы
   subshell не оставался прослойкой между `$!` и настоящим процессом
   `claude`, независимо от версии bash), затем цикл опроса
   `kill -0 "$claude_pid"` с шагом `0.2s` сравнивает
   `SECONDS - task_iter_start` с бюджетом; превышение — `SIGTERM`, до пяти
   опросов по `0.2s` на грациозное завершение, затем `SIGKILL`, только если
   процесс всё ещё жив (безусловный `kill -9` после цикла ожидания способен
   попасть в чужой PID, который ОС уже успела переиспользовать, если
   процесс был прибран раньше — круг 1 ревью PR #193). `$SECONDS` —
   bash-таймер целых секунд от старта интерпретатора, не требует внешних
   команд и работает одинаково на macOS/Linux/CI. Отклонённая альтернатива
   — `timeout <N>m claude -p ...` с фолбэком на `command -v gtimeout`: два
   пути кода вместо одного, при этом ветка без обеих команд всё равно
   обязана быть kill-based — альтернатива не устраняет сложность, а
   добавляет её.
   - **Сигнал бьёт группу процессов, не только сам `claude`** (круг 1
     ревью PR #193): фоновый job получает собственный PGID, равный PID
     лидера, только на время своего запуска под `set -m` (решение 5
     ниже — не на весь скрипт), и `kill -- "-$claude_pid"` (отрицательный
     PID = группа процессов) валит лидера и всех его потомков одним
     сигналом. Без этого `claude -p` мог успеть запустить дочерние
     процессы (команды инструментов, тестовые раннеры, dev-серверы),
     которые сигнал, адресованный только PID лидера, не касается вовсе —
     они переподвешивались к PID 1 и продолжали писать в дерево
     параллельно со следующей итерацией цикла. Обе фикстуры круга 1
     (`RALPH_BUDGET_TASK`/`RALPH_BUDGET_RUN`, `tests/run.sh`) используют
     `exec sleep N` в стабе `claude` — `exec` замещает образ процесса
     самого стаба, у него нет ни одного потомка, group-kill там убивает
     единственный процесс группы, и группу из одного элемента не отличить
     от группы из нескольких; вопреки более ранней версии этого пункта,
     ни одна из них НЕ проверяла собственно group-kill (круг 2 ревью
     PR #193). `RALPH_BUDGET_GROUPKILL` (`tests/run.sh`) добавлена
     отдельно: стаб `claude` форкает настоящий дочерний `sleep 30` в фоне
     (не `exec`) и ждёт его; фикстура проверяет, что после group-kill
     погиб именно этот дочерний PID, а не только PID лидера.
   - **Сигнал самому ralph (Ctrl-C) — явная ловушка, а не расчёт на
     наследование** (круг 1 ревью PR #193): до этой задачи `claude -p`
     выполнялся синхронно на переднем плане, и `INT`/`TERM`, посланные
     ralph, доходили и до него как до члена той же foreground-группы.
     Бэкграундинг для опроса бюджета ломает это: фоновый job на время
     своего запуска получает собственную группу, изолированную от
     управления терминалом. `trap ... INT TERM` на уровне скрипта явно
     добивает `$claude_pid` (и его группу, если она ещё жива) при
     получении сигнала и пишет `event=run_end` перед выходом — без этого
     Ctrl-C по ralph оставлял бы `claude -p` сиротой без единой записи в
     журнал о прерванном прогоне. Exit-код обработчика — конвенция
     `128+N`: `130` для `INT` (`128+2`), `143` для `TERM` (`128+15`) —
     круг 2 ревью PR #193 нашёл, что более ранняя версия отдавала
     буквальный `130` для обеих веток. Круг 4 ревью PR #193 нашёл ещё один
     пробел того же класса, не покрытый ни одной фикстурой: `event=run_end
     done=0` писалось безусловно, вне зависимости от факта merge — после
     интеграции issue #129 (merge ready-PR) сигнал, пришедший ПОСЛЕ
     успешного merge этим же прогоном, искажал бы журнал буквальным нулём.
     Обработчик теперь пишет `done="${merged_count:-0}"`, тем же полем, что
     и штатный хвост цикла в конце файла; воспроизведено фикстурой
     `RALPH_SIGNAL` (`tests/run.sh`): реальный merge, затем настоящий
     `SIGTERM` самому процессу во время исполнения следующей задачи.
     Значение `reason="прерван сигналом $sig"` (уже писавшееся кодом с
     круга 1, но никогда не внесённое в реестр) добавлено в ADR-007 §3 и
     ADR-001 этим же кругом — см. «Последствия».
2. **Бюджет прогона проверяется только на границе выбора следующей
   задачи, никогда не сокращает уже выделенный бюджет текущей.** Проверка
   `SECONDS - run_start_seconds >= run_budget_seconds` стоит на границе
   итерации, ПОСЛЕ стоп-файла и системного breaker'а красных гейтов main
   (`run_main_gates`) — точный порядок всех проверок этой границы, включая
   место бюджета прогона в нём, зафиксирован п.6 ниже (рёбейз PR #193 поверх
   issue #130/#135 потребовал явного решения) — но раньше `select_next`, до
   `claude -p`. Она не участвует в вычислении `task_budget_seconds` (константа для всех
   задач прогона, не `min(task_budget, остаток_run_budget)`): задача,
   уже отобранная и запущенная, всегда получает полный бюджет задачи, даже
   если это заведомо продлит прогон за пределы бюджета прогона — прогон
   останавливается чисто на СЛЕДУЮЩЕЙ попытке выбора, не обрывает текущую
   на середине. Ровно так читается формулировка issue «текущая доводится,
   остаток задачу не режет». Проверка `>=`, не `>` — исчерпание ровно на
   границе (бюджет истёк аккурат к моменту выбора следующей задачи)
   останавливает цикл, а не откладывается до следующей секунды опроса.
   Код выхода — `1` (не `0`, как у штатной «очередь пуста»): очередь
   доигрывается не до конца, а обрывается по внешнему ограничению — тот же
   класс исхода, что и у breaker'ов (ADR-015/ADR-016), которые уже
   используют `1` для «прогон остановлен ДО того, как сам исчерпал
   доступные задачи», сигнализируя внешнему наблюдателю (cron-обвязка,
   человек), что оставшаяся очередь не тронута и достойна отдельного
   внимания, в отличие от «очередь пуста», где обработано реально всё.
3. **Ноль/отрицательное значение — ошибка конфига (опечатка), не «без
   лимита»; та же дисциплина (текст предупреждения в stderr + откат на
   дефолт), что у `maxStuckPerRun`/`maxSkippedShare` (ADR-016), хотя это
   отдельная копия python-валидатора, а не общий код.** SPEC-003 называет
   бюджеты жёсткими («превышение всегда останавливает, "мягких
   предупреждений" нет») и не описывает отдельного способа их отключить —
   если бы `0`/отрицательное значило «без лимита», это был бы
   недокументированный побочный вход в поведение, которого спека не
   предусматривает, и он был бы неотличим от опечатки в конфиге (человек по
   ошибке поставил `0` вместо `40`). Невалидное значение (нечисловое, ноль,
   отрицательное) — предупреждение в stderr, использован дефолт
   (`45`/`240`). Отдельно — `"nan"`/`"inf"` (круг 1 ревью PR #193): проверка
   `<= 0` их не ловит (сравнение с `nan` всегда `false`, `inf > 0`
   истинно). Уточнение (issue #212): без `math.isfinite` они всё равно
   попали бы в тот же `except (… ValueError, OverflowError)` у
   `int(round(...))` с тем же предупреждением — явная проверка на
   конечность нужна не против «необработанного исключения», а чтобы
   «не число минут» ловилось осмысленной валидацией, а не побочным
   исключением арифметики ниже. Верхняя граница
   `10**9` секунд (~31 год) на результат — защита от абсурдно большого, но
   конечного значения, которое не влезло бы в 64-битную арифметику `$(( ))`
   остального кода. Клампинг `min(seconds, 10**9)` применяется ПОСЛЕ
   `int(round(minutes * 60))`, а не до него — круг 2 ревью PR #193 нашёл,
   что для конечных, но астрономических значений (`"1e307"`/`"1e308"`)
   `minutes * 60` как `float` сам переполняется в `inf` ДО этой границы,
   `int(round(inf))` кидает необработанный `OverflowError` — тот же класс
   бага, что уже чинили для `nan`/`inf` выше. Исправление — считать
   `seconds` внутри того же `try`, что и саму валидацию `minutes`, и ловить
   `OverflowError` той же веткой, что `TypeError`/`ValueError`: одна и та же
   строка предупреждения покрывает оба случая (не число vs переполнение при
   умножении), верхняя граница `10**9` по-прежнему применяется к
   результату — она защищает от большого, но НЕ переполняющего float
   значения (например, годы, не эры).
4. **Грязное рабочее дерево после прерывания по бюджету задачи —
   обычный `result=stuck` (needs-human/уведомление/`event=task`)
   отрабатывает целиком КАК ОБЫЧНО, и только ПОСЛЕ него — честная
   остановка всего прогона БЕЗ `return_to_default_branch`.** Штатный
   `result=stuck` (PR остался черновиком/не создан) предполагает, что
   `claude -p` завершился САМ — по рецепту `work.md` дерево к этому
   моменту либо чистое, либо на ветке задачи с закоммиченными шагами.
   Прерывание по бюджету убивает процесс ПОСРЕДИ работы: незакоммиченные
   правки (неотслеживаемые файлы, изменённые отслеживаемые) могут остаться
   на дереве. `return_to_default_branch` (issue #144) делает
   `git checkout <default>` безусловно и не проверяет чистоту дерева —
   такие правки молча переехали бы на default branch, если не расходятся
   с ним, заражая следующую итерацию. Первая версия этого решения (круг 1
   ревью PR #193) делала `break` СРАЗУ при обнаружении грязного дерева —
   раньше `needs-human`/уведомления/счётчиков/`event=task result=stuck`.
   Круг 2 ревью PR #193 признал это блокером: прерванный посреди работы
   `claude -p` почти всегда оставляет дерево грязным — это ОСНОВНОЙ
   реальный путь застревания по бюджету задачи, и на нём DoD issue #131
   (`needs-human`/уведомление/`result=stuck`) не выполнялся вовсе — issue
   оставался без метки, следующий прогон брал бы его заново уже на
   заражённом дереве. Исправление: `git status --porcelain` проверяется и
   ЗАПОМИНАЕТСЯ (`budget_dirty_tree`) сразу после прерывания, `pr_state`
   остаётся `"budget-exceeded"` и идёт по тому же общему stuck-коду, что
   «PR остался черновиком»/«PR не создан» (needs-human, уведомление,
   счётчики, `event=task result=stuck`); только ПОСЛЕ этого блока, читая
   `budget_dirty_tree`, — остановка всего прогона, и КОНКРЕТНО без вызова
   `return_to_default_branch` (не после него): дерево остаётся НЕТРОНУТЫМ
   ровно так, как его оставил прерванный процесс — не коммитим и не
   force-чекаутим за человека (тот же принцип, что и у самого
   `return_to_default_branch` — данные потенциально ещё нужны). Дерево
   чистое — `budget_dirty_tree` пуст, второй `break` не срабатывает,
   обычный путь продолжается до `return_to_default_branch` и следующей
   задачи. Воспроизведено фикстурой `RALPH_BUDGET_DIRTY` (`tests/run.sh`):
   #961 получает needs-human/уведомление/`event=task result=stuck` (тот же
   DoD, что на чистом дереве), и только затем прогон останавливается
   целиком, #962 не берётся вовсе, дерево остаётся заражённым нетронутым.
5. **`set -m` (job control) — только вокруг самого фонового запуска
   `claude -p`, не на весь скрипт.** Круг 1 ревью PR #193 включил `-m`
   безусловно сразу после `set -u` в шапке файла, обосновав это «не меняет
   поведение ни одной другой команды скрипта». Круг 2 нашёл это неверным и
   признал важным (не блокером, но требующим исправления) находкой:
   безусловный `-m` под tty даёт КАЖДОМУ foreground-job'у скрипта
   (`gh issue edit`, `gh label create`, `"$logger"`, `"$notifier"`,
   python-валидаторы `run_breaker_check_*`, стартовый `gh issue list`)
   собственную группу процессов и терминал — INT/TERM с терминала до них
   больше не долетают тем же путём, что раньше; вдобавок под `-m` bash
   перестаёт по умолчанию перенаправлять stdin фонового job'а в
   `/dev/null` — процесс, читающий tty, способен тихо застопориться
   (`SIGTTIN`). Исправление — `set -m` включается непосредственно перед
   `&`, которым запускается `claude -p`, и выключается (`set +m`) сразу
   после захвата `$!`; фон получает свою группу процессов ровно в момент
   форка (это фиксируется при создании процесса и не меняется последующим
   `set +m`), а все остальные команды скрипта снова выполняются с job
   control выключенным, как до круга 1. Явный `</dev/null` на самом
   фоновом job'е — не подстраховка, а прямое следствие той же находки:
   пока `-m` включён для его запуска, автоматический редирект stdin в
   `/dev/null`, который bash даёт background job'ам только при
   выключенном job control, не происходит сам по себе.
6. **Порядок проверок на границе итерации — стоп-файл → системный breaker
   (красные гейты main) → бюджет прогона.** Рёбейз PR #193 поверх issue
   #130 (стоп-файл) и issue #135 (системный breaker) потребовал явного
   решения, а не только текстового слияния. Стоп-файл остаётся первой
   проверкой безусловно (ADR-018 — явное намерение человека сильнее любой
   автоматики). Между системным breaker'ом и бюджетом прогона решение —
   системный breaker ПЕРВЕЕ: он сигнализирует, что сама инфраструктура
   прогона сломана (гейты main красные) — тем же принципом, что уже
   применяется в хвосте итерации (`actualization_breaker_tripped`
   проверяется раньше `run_breaker_reason`, оба — ADR-015/ADR-016:
   «системный уровень серьёзнее уровня прогона»). Бюджет прогона — тоже
   уровень прогона (безусловный потолок длительности, но не про
   содержимое очереди), поэтому логично подчиняется тому же порядку: при
   коллизии (гейты красные И бюджет прогона истёк одновременно) сводка
   обязана называть системный breaker, не исчерпанный бюджет —
   `run_main_gates` обязан выполниться и вернуть свой результат раньше, чем
   станет известно, сигнализирует ли он вообще что-то (сами гейты красные
   узнаются только по факту их прогона); откладывать эту проверку ради уже
   всё равно проигравшей при коллизии причины (бюджет) значило бы иногда
   пропускать более серьёзный системный сигнал ради экономии времени,
   которое всё равно частично уже потрачено бюджетом прогона.

## Последствия

- Бюджет задачи покрывает только сам headless-процесс `claude -p`:
  merge-ветка ready-PR (issue #129, ADR-019) и предстартовая обработка
  уже-ready issue (ADR-014) в него не входят — их длительность ограничена
  только бюджетом прогона (оговорка issue #212).

- Новые атрибуты `policies.autopilot.budget.task.maxMinutes` (дефолт `45`)
  и `policies.autopilot.budget.run.maxMinutes` (дефолт `240`) — только
  `hooks/scripts/adk-ralph.sh` их читает (`docs/config.md`); оба дефолта
  калибруются по `/stats` после первых прогонов (SPEC-003 «Переходные
  состояния»), это не окончательные цифры.
- Два новых значения `event=run_end.reason` — аддитивное расширение
  ADR-001 «Расширения схемы», реестр ADR-007 §3 обновлён синхронно:
  `"бюджет прогона по времени"` (п.2) и `"бюджет задачи по времени: рабочее
  дерево не чисто после прерывания issue #N"` (п.4). Оба места (код,
  ADR-007, ADR-001) правятся синхронно, той же дисциплиной, что и
  предыдущие расширения этого реестра — но само число «всего значений» в
  ADR-007 §3 к моменту этой задачи уже не совпадало с фактическим
  количеством различимых `stop_reason` в коде (пропущено значение issue
  #144 «не удалось вернуть дерево…») — расхождение существовало ДО этой
  задачи, не создано ею, и его исправление (полный аудит и бэкфилл
  реестра) — отдельная задача, не блокирующая эту (выполнена: issue #211,
  граница CONS-002 — реестр ADR-007 §3 сверен с кодом полностью).
- Круг 4 ревью PR #193 добавил третье значение того же реестра —
  `"прерван сигналом <SIG>"` (`INT`/`TERM`, обработчик `ralph_signal_cleanup`)
  — писавшееся кодом уже с круга 1, но никогда не внесённое в ADR-007 §3/
  ADR-001; заодно исправлено `event=run_end done` на этом же событии
  (безусловный `0` → `"${merged_count:-0}"`, тот же баг класса «поле не
  обновили после интеграции issue #129», что уже чинили для `stop_reason` в
  других местах). Реестр ADR-007 §3 и ADR-001 обновлены синхронно;
  фикстура — `RALPH_SIGNAL` (`tests/run.sh`).
- `result=stuck reason="бюджет задачи по времени"` на `event=task` — та же
  свободнотекстовая форма поля `reason`, что уже используют «PR остался
  черновиком»/«PR не создан» (ADR-007 §2-3); отдельного реестра для причин
  `event=task` в ките нет, регистрировать не требуется.
- `set -m` (job control) включён ТОЛЬКО на время фонового запуска
  `claude -p` (п.5) — не затрагивает остальные foreground-команды
  `adk-ralph.sh`. `trap ... INT TERM` на уровне скрипта (п.1) — постоянное
  изменение, необходимое именно из-за бэкграундинга `claude -p`, введённого
  этой задачей; обработчик отдаёт `128+N` (`130`/`143`), не буквальный
  `130` для обеих ветвей.
- Опрос `0.2s` — фиксированный шаг кода, не атрибут конфига: точность
  порядка десятых долей секунды достаточна для бюджетов, измеряемых в
  минутах, тем же принципом, что константы `actualization_conflict_threshold`
  (ADR-015) и `run_breaker_min_denominator` (ADR-016) — защитная точность
  реализации, не настраиваемая политика прогона.
- Порядок проверок на границе итерации (п.6) — стоп-файл, системный
  breaker, бюджет прогона — задокументирован здесь, а не в ADR-015/ADR-018:
  оба существовали до этой задачи и не описывали взаимный порядок с
  бюджетом, которого тогда не было; будущая четвёртая проверка того же
  рода обязана явно решить своё место в этой же цепочке, а не полагаться
  на порядок текстовых вставок при рёбейзе.
- Остальные задачи плана SPEC-003 (токеновый бюджет — issue #132,
  множитель `size:large` — issue #133, стоп-файл — issue #130, merge —
  issue #129) не затронуты — работают поверх этой версии без изменений.
