# ADR-003: result=ready в журнале /autopilot для PR, ждущих человека

Дата: 2026-08-14
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

SPEC-002 (AC-3) вводит `policies.autopilot.canMerge=false`: `/autopilot`
не мержит ready-PR, а собирает их в список «ждут человека»; задача при
этом не застряла. Схема журнала ADR-001 знает для `event=task` только
исходы `merged|stuck|skipped` — ни один не описывает «PR готов, merge
за человеком»: `merged` — ложь, `stuck` требует reason и означает
эскалацию, `skipped` — задача не бралась.

## Решение

Расширить схему ADR-001 (не заменить — supersedes не нужен, ADR-001
явно допускает обратимое расширение) двумя добавками в
`autopilot-<дата>.jsonl`:

- `event=task issue=<N> result=ready` — задача доведена до ready-PR,
  merge оставлен человеку (из-за `canMerge=false` или блокировки
  `gh pr merge` хуком по `policies.merge`);
- `event=run_end ... ready=<k>` — счётчик таких PR в итоге прогона.

Отклонённые альтернативы:
- `result=merged` с полем-маркером — враньё в основном поле ради
  экономии значения;
- `result=stuck reason="ждёт человека"` — смешивает штатный режим
  политики с эскалацией, портит агрегат застреваний;
- не логировать такие задачи — дырка в журнале прогона (одна строка на
  каждую обработанную задачу — инвариант ADR-001).

## Последствия

- `adk-stats.sh` агрегирует задачи только по `issue-*.jsonl` (ADR-001),
  поэтому новое значение в `autopilot-*.jsonl` его агрегатов не меняет;
  захочет показывать «ждут человека» — прочитает `ready` осознанно.
- Читатели журнала не должны считать перечень значений `result` в
  `event=task` закрытым.
