# ADR-022: гейт фронтматтера — белый список эмпирически безопасных форм

Дата: 2026-09-30
Обновлено: 2026-10-01 (круг 6 — эмуляция алгоритма рантайма; круг 7 —
переход на белый список; круг 8 — четыре дополнительных правила по
итогам повторной независимой проверки)
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #201: блокер круга 2 PR #199 — перевёрстка сломала фронтматтер
`commands/stats.md` (строка-продолжение потеряла отступ и встала на
колонку 0), команда теряла `description`/`argument-hint` в рантайме
Claude Code, а ни `scripts/check`, ни тесты кита этого не увидели. Нужен
локальный гейт, парсящий фронтматтер `commands/*.md`, `agents/*.md`,
`skills/*/SKILL.md` и проверяющий обязательные по типу ключи.

### История подхода (восемь кругов ревью)

**Круги 1–5** реализовывали гейт растущим чёрным списком точечных
эвристик («есть ли `: ` в строке», «кончается ли строка на `:`», ...).
Каждый круг ревью реверс-инжинирингом рантайма (бинарь 2.1.114, Bun
1.3.13, `strings` по функциям рантайма) находил соседний непокрытый
кейс того же класса: гейт оставался терпимее реального рантайма. Круг 5
нашёл девять новых дыр разом и порекомендовал: вместо накопления
эвристик — точно смоделировать сам двухфазный алгоритм рантайма
(строгий `Bun.YAML.parse`, затем построчный fallback-парсер по
регэкспу-триггеру).

**Круг 6** реализовал именно это: прямую эмуляцию двухфазного алгоритма
на python3 stdlib. Независимая проверка (реверс-инжиниринг того же
бинаря, плюс дифференциальный фаззинг) нашла: модель алгоритма была
неверна в ключевом месте. Триггер `U_1` — это условие того, когда
построчный fallback перепишет строку, а не предсказатель того, что
строгий парсер на ней упадёт. Многие символы `U_1` (`#`, `[`, `{`, `&`,
`!`, `|`, `>`) в строгом YAML не бросают исключение — комментарий `#`
молча обрезает значение, `[...]`/`{...}` успешно парсятся как
массив/объект (а не строка). Во всех этих случаях строгая фаза не
падает, fallback вообще не запускается, а дальнейший код рантайма молча
превращает такое значение в `null` или обрезанную строку. Эмуляция
круга 6 считала такие значения «спасёнными fallback-ом» — неверно
вдвойне. Фаззинг нашёл ≈4,5% случайных документов с этим паттерном.

**Круг 7**: отказ от попытки эмулировать сам парсер в пользу белого
списка форм, которые доказуемо (по построению самой формы, не по
предсказанию поведения парсера) не зависят от деталей конкретного
парсера — независимо предложен и кругом 5, и кругом 6 ревью. Независимая
проверка круга 7 нашла: даже это не покрывает всё. Bun.YAML 1.3.13 на
практике **не полностью соответствует спецификации YAML** — например,
`...` (маркер конца документа по спецификации — только в начале строки)
трактуется им как конец документа и внутри plain-значения, если после
него пробел или конец строки. Из-за этого расхождения часть
рассуждений «форма безопасна по спецификации» не была безопасной именно
для этого рантайма. Также нашлись: YAML-числа (`1.0`, `0x1F`, `.inf` и
т.д., типизируемые строгим парсером как `number`, а не строка) и
CRLF/юникодные разделители строк (построчные регэкспы рантайма — JS, где
`.` не матчит `\r`/` `/` ` — ведут себя иначе, чем python3 с
универсальными переводами строк).

**Круг 8** (текущее состояние): добавлены четыре правила, закрывающие
находки круга 7, и исправлена формулировка свойства, которое
обеспечивает белый список — не «математически доказанная безопасность
по спецификации YAML» (неверно для этого конкретного рантайма), а
**эмпирически проверенная безопасность против Bun.YAML 1.3.13** —
реверс-инжинирингом бинаря и дифференциальным фаззингом против реально
установленного Bun той же версии (методика — ниже).

### Источник: дословные фрагменты рантайма (бинарь 2.1.114, `strings -n 20`)

Фрагменты, извлечённые из `~/.local/share/claude/versions/2.1.114` и
независимо подтверждённые дважды (кругами 6 и 7 ревью):

- Триггер построчной перезаписи fallback-парсера (пробелы в записи ниже
  — только для читаемости, в бинаре без них):
  `` U_1 = /[{}[\]*&#!|>%@`]|: / ``
- Ленивая граница фронтматтера: `phH = /^---\s*\n([\s\S]*?)---\s*\n?/`
  — первое вхождение `---` где угодно в тексте после открывающей строки,
  не обязательно отдельной строкой.
- Строгий парсер — реально `Bun.YAML`, не npm `yaml` (рантайм собран на
  Bun): `csH(H){if(typeof Bun<"u")return Bun.YAML.parse(H);...}`.
- `d_1` — построчный fallback: регэксп `^([a-zA-Z_-]+):\s+(.+)$`
  матчится только на строке колонки 0 вида «ключ: значение»; строки-
  продолжения (с отступом) этот регэксп никогда не матчит и никогда не
  кавотирует.
- `lz` — fallback запускается только по исключению строгого парсера
  (`try { strict } catch { try { fallback } catch { LOST } }`); если
  строгий парсер вернул не-объект (например массив — ровно то, что
  получается из документа, разрезанного `...` надвое) без исключения —
  fallback не запускается вовсе, результат — пустой `{}` без
  диагностики.
- Постобработка значений (`w4_`/`cW9`/загрузчик скиллов): `description`
  — `string → .trim() || null`, `number/boolean → String(...)`, всё
  остальное (`null`, массив, объект) → `null`, при `null` рантайм молча
  подставляет описание из первой строки тела команды; `argument-hint`
  — `!= null ? String(...) : undefined`; у агента `model` берётся только
  при `typeof string`, `tools` — через отдельный разбор, не строкой;
  `name` скилла — только при `typeof string`, иначе берётся из каталога.

## Решение

1. **Гейт принимает значение, только если оно — форма, эмпирически
   проверенная как безопасная против Bun.YAML 1.3.13**, не «форма,
   которую гейт предсказывает как переживающую разбор по общей
   спецификации YAML» (круг 7 ошибочно использовал слово «доказуемо» в
   этом втором, более сильном и неверном смысле — см. «Последствия»).
   Реализация — `hooks/scripts/frontmatter-check.sh` (bash-обвязка над
   инлайн `python3 -c`, без внешней зависимости: `yaml`/`pyyaml` не
   входит в stdlib python3 и не нужен ради одной этой проверки).

   Значение записи (первая строка после `ключ:` плюс все строки-
   продолжения) принимается, если выполняется одно из:

   **(а) Однострочное кавыченное значение.** Начинается и заканчивается
   одним и тем же символом кавычки (`"..."` или `'...'`), без строк-
   продолжений, и внутри нет ни второй такой же кавычки, ни (для
   двойных кавычек) обратного слеша — без экранирования и без риска,
   что закрывающая кавычка на самом деле не последняя. Всё, что не
   укладывается в эту точную форму (незакрытая кавычка, хвост текста
   после закрывающей, валидный YAML-escape внутри, перенос на другую
   строку) — отказ, не попытка угадать результат.

   **(б) Plain-значение без признаков риска**, однострочное или с
   опциональными строками-продолжениями (только пробельный отступ, без
   табов). Этой форме соответствуют и `commands/autopilot.md`, и
   `commands/work.md` — их `description` однострочный, без продолжений,
   с `: ` как единственным риск-символом. Правила:
   - ни одна строка записи не содержит одиночных символов
     `{ } [ ] * & # ! | > % @` или обратной кавычки — ни в какой
     позиции (строгий парсер по ним не обязан бросать исключение, может
     молча вернуть не то значение, минуя fallback целиком);
   - ни одна строка записи не содержит подстроку `...` — Bun.YAML 1.3.13
     трактует её как маркер конца документа даже внутри значения,
     строгий разбор отдаёт несколько «документов» вместо объекта,
     fallback не запускается (найдено кругом 7-ревью);
   - `: ` (двоеточие с пробелом) допускается ТОЛЬКО если у записи нет ни
     одной строки-продолжения — единственная форма, где fallback
     рантайма (`d_1`) реально перезаписывает строку колонки 0 и спасает
     значение;
   - ни одна строка записи не заканчивается голым `:` (после удаления
     хвостовых пробелов) — фатально всегда, с продолжением или без;
   - первый непустой символ значения (первая строка, если непуста,
     иначе первая непустая строка-продолжение — обрабатывает легальный
     `description:` с текстом на следующей строке) не входит в набор
     `- ? : , [ ] { } # & * ! | > ' " % @` и не обратная кавычка;
   - собранное значение целиком не совпадает с YAML null/bool-литералом
     (`~`, `null`, `Null`, `NULL`, `true`/`false` и варианты регистра) —
     иначе строгий парсер отдаёт не строку, а `None`/`True`/`False`;
   - собранное значение целиком не совпадает с YAML-числом (`1.0`,
     `0x1F`, `1e3`, `010`, `+1`, `.inf`, `.nan` и т.п.) — YAML core
     schema типизирует такой токен как `number`, строгий парсер отдаёт
     не строку (найдено кругом 7-ревью).

   **Граница фронтматтера.** Первое вхождение `---` после открывающей
   строки обязано быть отдельной строкой (сам символ `---` и только
   пробельный хвост до конца строки) — если найденное вхождение стоит
   посреди строки (внутри значения), это означает, что рантайм
   (`phH`, точно так же лениво ищущий первое вхождение где угодно)
   обрежет значение прямо там же, молча — гейт обязан заметить и
   отказать, а не согласиться с уже обрезанным текстом как с
   «безопасным значением» (найдено кругом 7-ревью: описание,
   заканчивающееся обрывком вида `Гейт --- проверка фронтматтера`, где
   `---` стоит в последнем ключе файла, иначе осталось бы незамеченным —
   пропавшего следующего обязательного ключа тут нет, чтобы на него
   сработала проверка `REQUIRED`).

   **Файл целиком.** Если в файле встречается `\r`, ` `, ` `
   или `\u0085` — отказ безусловно, до попытки разбора: построчные
   регэкспы рантайма (JS, где `.` не матчит эти символы) обрабатывают
   такой файл иначе, чем python3 с универсальным переводом строк по
   умолчанию (который гейт поэтому явно отключает при чтении файла) —
   безопасность формы в этом случае эмпирически не проверена (найдено
   кругом 7-ревью; реалистичный сценарий — checkout на Windows с
   `core.autocrlf=true` без `.gitattributes` в репозитории).

2. **Белый список допустимых ключей по типу файла (`ALLOWED`)** —
   отдельная, более строгая защита от класса бага PR #199, не часть
   анализа безопасности значения: строка-продолжение, потерявшая отступ
   и ставшая синтаксически валидным новым `ключ: значение`, отвергается
   как неизвестный ключ, даже если `Bun.YAML` разобрал бы такой документ
   без единой ошибки.
3. **Обязательные ключи — по типу файла, не общий список.**
   `commands/*.md`: `description`, `argument-hint`. `agents/*.md`:
   `name`, `description`, `model`, `tools`. `skills/*/SKILL.md`: `name`,
   `description`. Список — из issue #201, зафиксирован константой
   `REQUIRED` (тот же набор, что и `ALLOWED`, пока в ките нет
   опциональных ключей); пустое значение (включая пустую строку в
   кавычках) считается отсутствующим.
4. **Повторяющийся ключ — предупреждение, не ошибка.** Независимая
   проверка установила: на Bun.YAML 1.3.13 дублирующиеся ключи не
   приводят к потере документа — побеждает последнее значение, и в
   строгой фазе, и после fallback. Поведение гейта (последнее значение
   побеждает плюс предупреждение в stderr) совпадает с рантаймом по
   факту — не отдельное исключение из белого списка, а наблюдаемое
   поведение.

## Методика эмпирической проверки

Белый список не выводится из спецификации YAML (круг 7 ошибочно
рассуждал именно так) — он проверяется против реально установленного
`Bun` той же версии, что рантайм (`1.3.13`), двумя независимыми
способами, оба повторены дважды разными проверяющими (круги 6 и 7):

1. **Реверс-инжиниринг.** `strings -n 20` по бинарю рантайма
   (`~/.local/share/claude/versions/<версия>`) — дословные фрагменты
   `U_1`/`phH`/`csH`/`d_1`/`lz` и постобработки значений (раздел
   «Источник» выше).
2. **Эмулятор + дифференциальный фаззинг.** JS-эмулятор, дословно
   воспроизводящий найденные фрагменты поверх настоящего
   `Bun.YAML.parse` (сам `Bun` версии рантайма устанавливается в
   scratchpad, не в репозиторий кита). Генератор случайных фронтматтеров
   варьирует: словарные токены, числа во всех YAML-формах, `...`/`--`/
   `---`/`- `/`? `/`: `, кавычки, обратный слеш, CRLF, NBSP, юникодные
   разделители строк, 0–2 строки-продолжения, все три типа файлов
   (`command`/`agent`/`skill`) и порядок ключей. Оракул — тип и значение
   каждого обязательного ключа после полного цикла рантайма (`lz` +
   постобработка). На выборках по 2000–4000 документов на сид
   единственное направление расхождения, которое считается блокером —
   «гейт принял форму, рантайм потерял или исказил значение»; обратное
   направление (гейт отверг форму, которую рантайм на деле разобрал бы
   верно) — ожидаемая, документированная цена консервативности, не
   блокер.

   На момент круга 8 (белый список с четырьмя дополнительными правилами
   — «...», YAML-числа, `---` не отдельной строкой, CRLF/юникод-
   разделители) на нескольких прогонах по 3000 случайных документов на
   каждый тип файла и на разных сидах не найдено ни одного случая
   «гейт принял, рантайм потерял/исказил».

   Эмулятор и фаззер не входят в репозиторий кита — инструмент разовой
   проверки, не часть контракта. При появлении новой версии рантайма с
   другим алгоритмом строгого парсера или fallback имеет смысл повторить
   проверку заново, а не считать её выводы верными бессрочно для любой
   будущей версии.

## Последствия

- Гейт не эквивалентен ни чтению исходного кода рантайма, ни полному
  YAML, ни строгому соответствию спецификации YAML — он эмпирически
  проверен как не терпимее рантайма (Bun.YAML 1.3.13) на принятых
  формах методикой выше, в объёме, который реально прогнан (разделы
  «Методика» и «Источник»); это не математическое доказательство на
  все возможные входы, и формулировка «доказуемо безопасно» в этом
  ADR (до круга 8) была избыточно сильной.
- Гейт строже самого себя на предыдущих кругах (1–7) в смысле охвата
  принимаемых форм: часть значений, которые реальный рантайм на деле
  разобрал бы правильно (например однострочное значение с одиночным
  `#`, если бы парсер почему-то не воспринял его как комментарий),
  белым списком отвергается. Это осознанный компромисс: ложное красное
  на редкой форме дешевле очередного круга «гейт терпимее рантайма».
- Гейт терпимее рантайма в одном явном месте — повторяющийся ключ:
  поведение на деле совпадает с рантаймом (последнее значение
  побеждает), гейт лишь добавляет предупреждение вместо тихой
  перезаписи, то есть не терпимее по результату, а просто более
  заметен. Белый список допустимых ключей (`ALLOWED`), наоборот, делает
  гейт строже рантайма, не терпимее (п. 2 «Решения»).
- Список обязательных/допустимых ключей — плоские константы в скрипте;
  расширение на новый тип файла, новый обязательный ключ или появление
  первого опционального ключа (`REQUIRED` ≠ `ALLOWED`) правит
  `REQUIRED`/`ALLOWED` и покрывающие тесты в одном месте, без отдельного
  конфига.
- Если когда-нибудь понадобится настоящая YAML-семантика (списки,
  вложенные структуры во фронтматтере, многострочные кавыченные
  скаляры, валидные escape-последовательности) — белый список придётся
  либо расширять новым эмпирически проверенным правилом (повторив
  методику выше против актуальной версии рантайма, не точечной
  эвристикой по одному наблюдению), либо, если расширение станет
  неподъёмным, подключать настоящий YAML-парсер; это уже другая, более
  широкая задача, не локальный гейт от перевёрстки описания — новый ADR
  с `supersedes ADR-022`.
