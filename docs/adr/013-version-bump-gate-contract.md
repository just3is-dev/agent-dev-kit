# ADR-013: version-bump-check.sh — вход, workflow отдельным файлом, base/head по SHA PR

Дата: 2026-09-20
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #151 (SPEC-004, docs/specs/004-plugin-versioning.md, AC-1) вводит
CI-гейт: PR, меняющий «файлы плагина» (перечень — docs/contract.md), обязан
менять `version` в `.claude-plugin/plugin.json`. Issue задаёт решение
частично буквально (скрипт в `.github/scripts/`, фикстурный вход — список
путей и две версии, без сети/git внутри; workflow — тонкая обёртка), но
оставляет открытыми: как именно скрипт получает список путей (аргументы
vs stdin), где живёт workflow (существующий `ci.yml` vs отдельный файл) и
как workflow добывает base/head SHA и версии без `gh api`. Прецедент в
ките — `.github/scripts/release-check.sh` + `.github/workflows/release.yml`
(issue #155, ADR-008), но там сравнение идёт с `HEAD^` на push в main, а не
с base-веткой PR — другая механика получения ревизий.

## Решение

1. **Список путей — на stdin, версии — позиционными аргументами.**
   `version-bump-check.sh <base_version> <head_version>`, пути по одному на
   строку на stdin. Отклонённая альтернатива — все пути аргументами:
   упирается в лимит длины командной строки на больших диффах и не даёт
   естественного способа передать пустой список; stdin решает оба случая
   и тестируется тем же `printf '%s\n' ... | script` паттерном, что уже
   есть в `tests/run.sh` для других хуков кита.
2. **Workflow — отдельный файл `.github/workflows/version-bump-check.yml`,
   не job в `ci.yml`.** `ci.yml` триггерится и на `pull_request`, и на
   `push: branches: [main]` одним и тем же job'ом (`check`+`test`); у
   гейта бампа нет осмысленного поведения на push в main (там нет
   «base-ветки PR» для сравнения) — добавление его туда потребовало бы
   `if: github.event_name == 'pull_request'` внутри job'а `ci.yml` или
   отдельного job'а с тем же условием, что не проще отдельного workflow.
   Отдельный файл, триггерящийся только на `pull_request`, симметричен
   уже принятому в ките паттерну «одна забота — один тонкий workflow»
   (`release.yml` для релизов, ADR-008).
3. **base/head — `github.event.pull_request.base.sha` /
   `.head.sha`, не `origin/<base_ref>`.** Явные SHA из события `pull_request`
   однозначны независимо от того, из форка PR или нет, и не требуют
   разрешать `base_ref` в имя ref'а в чекауте. С `fetch-depth: 0` оба SHA
   уже есть в истории (тот же приём, что `release-check.sh` использует для
   поиска предыдущего тега, ADR-008 п.2) — `git show <sha>:path` и
   `git diff --name-only <base_sha> <head_sha>` работают без `origin/`.
   Двухточечный `git diff` (не трёхточечный `...`), потому что
   `github.event.pull_request.base.sha` GitHub уже даёт SHA merge-base на
   момент последнего события — сравнение с ним и есть «то, что реально
   принесёт PR».
   Отклонённая альтернатива — `gh api pulls/<n>/files` (даёт список файлов
   PR без чекаута базы): требует токен с доступом к API, страдает от
   пагинации на PR с >100 файлами (нужен цикл по страницам, лишний код в
   «тонкой обёртке») и не даёт `version` на base без отдельного вызова
   `gh api .../contents/...`. `git diff`/`git show` на `fetch-depth: 0`
   чекауте — один инструмент для обоих значений (пути и версии), без
   доп. вызовов API.
4. **Скрипт классифицирует «файл плагина» текстовым `case`, не читает
   docs/contract.md программно.** `docs/contract.md` — markdown для
   людей, не машиночитаемый формат; парсить его регулярками ради шести
   префиксов было бы более хрупким, чем `case`-паттерн, синхронизация
   которого с contract.md зафиксирована явным комментарием в начале
   скрипта (та же проблема расхождения источника правды, что issues
   #150/#166/#173 — комментарий делает обязанность синхронизации
   видимой на месте, а не полагается на память автора следующей правки).

## Последствия

- `version-bump-check.yml` предполагает `fetch-depth: 0` — с мелким
  чекаутом `git show`/`git diff` по `base.sha`/`head.sha` из истории вне
  глубины клона дадут ошибку, а не тихо неверный результат (`set -eo
  pipefail` в шаге workflow превращает это в красный CI, не в
  пропущенную проверку).
- Перечень «файлов плагина» задублирован в двух местах кита —
  `docs/contract.md` (источник правды) и `case` в
  `.github/scripts/version-bump-check.sh` — правка перечня в contract.md
  обязана сопровождаться правкой этого скрипта; комментарий в начале
  файла напоминает об этом, но ничего не проверяет автоматически.
- Гейт применяется только к новым PR (события `pull_request` после
  появления этого workflow) — прошлые PR без бампа не переоцениваются,
  как и оговорено в SPEC-004 «Переходные состояния».
