# ADR-019: adk-ralph.sh — merge ready-PR по policies.merge/canMerge, ретрай UNKNOWN, CI-watch отложен

Дата: 2026-09-27
Статус: accepted <!-- accepted | superseded by ADR-XXX -->

## Контекст

Issue #129 (SPEC-003 AC-1) достраивает исход `pr_state = "ready"` в
`adk-ralph.sh`: до этой задачи он всегда собирал ready-PR в бакет «ждут
человека» (ADR-014), даже при `policies.autopilot.canMerge=true` и
`policies.merge=agent-after-approve`, потому что merge никогда не был
реализован. Это дыра ровно в том слое, который закрывал SPEC-002:
`bash-guard.sh` (PreToolUse-хук) видит только Bash-вызовы агентских сессий,
а `gh pr merge`, выполненный `adk-ralph.sh` как обычным процессом вне
`claude -p`, хук не перехватывает — `policies.merge` обязан проверять сам
скрипт. Канонический алгоритм для человека-оркестратора описан дважды (шаг
6 `commands/work.md`, отличия автопилота — шаг 3 `commands/autopilot.md`);
нужно перенести его в bash, не переписывая, и решить три вопроса, которых
канон не касается буквально: (1) как отличить `human-review-required` с
человеческим approve от без него — у ralph нет контекста сессии, откуда
брать этот факт; (2) `gh pr view --json mergeable` иногда отвечает
`"UNKNOWN"`, пока GitHub считает mergeability, — сколько раз повторять
запрос, прежде чем сдаться; (3) как not бюджетно и safely внести это в
существующий bash-цикл, не сломав ~40 уже принятых фикстур `adk-ralph.sh`,
которые полагаются на «ready-PR никогда не мержится».

## Решение

1. **Fail-closed на неизвестное значение** — та же дисциплина, что
   `bash-guard.sh`: `policies.autopilot.canMerge` и `policies.merge`
   читаются через `adk_config_get` с allowed-списком; ненулевой exit
   (опечатка в значении, не отсутствие атрибута) → merge не выполняется,
   задача остаётся в бакете «ждут человека» (`result=ready`), как и
   `human-only`. Порядок проверок: сначала оба атрибута конфига (дёшево,
   без сети), потом — только если оба валидны и разрешают merge — номер PR
   и его статус (`gh`, сеть).
2. **`human-review-required` — approve берётся из `gh pr view --json
   reviewDecision`**, тем же признаком, что канонический `/autopilot` (шаг
   3) и `bash-guard.sh` уже используют для той же политики: `reviewDecision
   != APPROVED` → `result=ready`, не `stuck` — это штатный режим политики
   (ADR-003), не эскалация.
3. **`mergeable=UNKNOWN` — до 3 попыток с паузой 1с**, затем — застревание
   с причиной «не удалось определить конфликтность PR». Три — тот же
   порядок величины, что и другие консервативные дефолты этого скрипта
   (`actualization_conflict_threshold=2`, ADR-015); GitHub обычно
   досчитывает mergeability за секунды, дальнейшее ожидание не в бюджете
   одной задачи ralph, а бесконечный ретрай превратил бы временную
   неопределённость GitHub в зависшую итерацию цикла.
4. **CI-watch (`gh pr checks --watch` из шага 3 `/autopilot`) сознательно не
   реализован в этой версии.** Канон ждёт зелёного CI перед merge, когда CI
   настроен; надёжно отличить «CI не настроен» от «CI ещё не завершился»/
   «CI красный» через `gh pr checks` в скрипте, не отправляющем PR-ссылку
   человеку для суждения, оказалось отдельной по объёму задачей (разные
   версии `gh` и разное число once-required контекстов возвращают разные
   коды выхода на «нет ни одной проверки»). DoD issue #129 требует красные
   ЛОКАЛЬНЫЕ гейты (`scripts/check`/`scripts/test`) после актуализации, не
   CI — это реализовано полностью (см. п.6). Пропуск CI-watch — задокументи-
   рованное ограничение, не немая деградация: `adk-ralph.sh` мержит
   актуализированную ветку с зелёными ЛОКАЛЬНЫМИ гейтами, не дожидаясь CI
   отдельно. Follow-up — отдельная задача, если это создаст проблему на
   практике (мердж до завершения CI на актуализированной ветке).
5. **Флаг слияния — `adk_config_merge_method` (lib/config.sh), не хардкод
   squash** (DoD issue #129): та же функция, что уже вычисляет метод
   приземления для `--merge-method` (ADR SPEC-002 AC-6), переводится в флаг
   `gh pr merge`: `squash-merge → --squash`, `rebase-merge → --rebase`,
   `merge-commit → --merge`.
6. **Актуализация — тот же рецепт, что шаг 6 `/work` / шаг 3 `/autopilot`,
   адаптированный под то, что ralph не сидит на ветке PR между
   итерациями**: конфликтность и ветка — `gh pr view --json
   mergeable,headRefName` (объединено с `reviewDecision` в один вызов,
   `adk_gh_pr_fields`, приём из `bash-guard.sh`/`lib/paths.sh`); отставание
   — явный `git fetch origin` + `git rev-list --count
   origin/<ветка>..origin/main` (не от HEAD); отставшая ветка —
   `gh pr checkout`, актуализация способом `conventions.branchUpdate`
   (fail-closed на опечатку — задача застревает, не прогон), гейты
   ЛОКАЛЬНО (`scripts/check`/`scripts/test`) до push, `git push
   --force-with-lease`/`git push` по способу актуализации — порядок «гейты
   → push», как в каноне. Конфликт с main, конфликт при актуализации и
   красные гейты после актуализации — `result=stuck` с причиной (needs-human,
   уведомление), прогон продолжается; успешный merge — `result=merged`,
   `gh pr merge <PR> <флаг> --delete-branch`.
7. **Единая точка для обеих веток `find_pr_state = "ready"`** (предстартовая
   ADR-014 §1 и обычная после `claude -p`) — `finish_ready_outcome`.
   Предстартовая ветка раньше делала `continue` в обход возврата дерева на
   default branch (ADR-007 §6): это было безопасно, пока reused-ready ничего
   не трогала в рабочем дереве. Merge способен выполнить `gh pr checkout` —
   без объединения веток предстартовый merge оставлял бы дерево на чужой
   ветке между итерациями. Обе ветки теперь сходятся в общий хвост цикла
   (`return_to_default_branch`, системный/run-level breaker) — тот же
   инвариант, что уже был у обычной ветки.
8. **`done=<merged_count>` вместо литерального `0`** — поле уже
   предусмотрено базовой схемой ADR-001 (`event=run_end done=<k> stuck=<k>
   skipped=<k>`); `result=merged` в `event=task` — тоже часть исходной схемы
   ADR-001 (`event=task issue=<N> result=merged|stuck|skipped`). Оба
   значения существовали в контракте с 2026-08-07, но `adk-ralph.sh`
   никогда их не производил (merge не был реализован) — эта задача не
   расширяет схему ADR-001, а реализует то, что схема уже предусматривала;
   новой записи в разделе «Расширения схемы» ADR-001 не требуется.
9. **Знаменатель `run_breaker_check_skipped_share` (ADR-016) расширен
   `merged_count`**: `ready_count + merged_count + stuck_count +
   skipped_count`. Смерженная задача доиграна до исхода прогона не менее
   определённо, чем ready-PR, ждущий человека — старая формула считала бы
   долю пропущенных завышенной на прогонах с реальным merge. На прогонах
   без merge (`merged_count` всегда 0) формула не меняет результат —
   обратной совместимости с существующими фикстурами это не нарушает.

Отклонённые альтернативы:
- Мержить без проверки актуальности ветки («PR уже прошёл ревью, зачем
  ещё раз гонять гейты») — отклонено: DoD issue #129 явно требует
  актуализацию + перегон гейтов при отставании, тот же принцип, что шаг 6
  `/work` («зелёные проверки отставшей ветки относятся к устаревшему
  состоянию кода»).
- Смешать `result=stuck reason="ждёт человека"` для fail-closed/human-only
  путей вместо `result=ready` — отклонено ADR-003: `stuck` уже значит
  эскалацию и портит агрегат застреваний, `ready` — штатный режим политики.
- Один порог retry на mergeable вместо фиксированных 3 попыток — отклонено:
  нет фактики, чтобы обосновать конфигурируемость; переходное состояние
  GitHub, не решение проекта (в отличие от `maxStuckPerRun`/
  `maxSkippedShare`, которые прямо калибруются под проект).

## Последствия

- Дефолт проекта (`canMerge=true`, `policies.merge=agent-after-approve`,
  ветка актуальна, гейты зелёные) с этой задачи реально мержит ready-PR из
  `adk-ralph.sh` — раньше это было объявленное, но нереализованное
  поведение. Существующие ~40 фикстур `adk-ralph.sh` в `tests/run.sh`,
  написанные до этой задачи, тестируют поведение цикла (SKIP/BLOCKED_ON_READY/
  breaker/стоп-файл), не merge — все они запускаются с явным
  `ADK_CONFIG_FILE`, отключающим merge (`policies.autopilot.canMerge=false`,
  экспортируется на весь блок ralph-фикстур в `tests/run.sh`, кроме тех, что
  сами задают свой `ADK_CONFIG_FILE`), чтобы не менять их назначение задним
  числом; новые фикстуры issue #129 явно включают merge своим конфигом.
- CI-watch — открытый пробел: `adk-ralph.sh` может смержить актуализированную
  ветку, чей CI на GitHub ещё не отчитался (только локальные гейты
  гарантированно зелёные к моменту merge). Если это создаст проблему на
  практике — отдельная задача добавит `gh pr checks --watch` с явным
  разбором «CI не настроен» от «CI ещё не закончился».
- `find_pr_number` дублирует запрос `gh pr list`, уже сделанный
  `find_pr_state` той же итерацией (тот же компромисс, что ADR-014 приняла
  для предстартовой проверки) — лишний вызов `gh`, не лишний вызов `claude`.
- Читатели `autopilot-<дата>.jsonl` не должны считать `done`/`result=merged`
  новыми полями — они существуют в схеме с ADR-001, только не
  производились до этой задачи.
