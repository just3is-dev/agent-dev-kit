# agent-dev-kit

Плагин Claude Code для проектов, которые разрабатываются ИИ-агентами.
Даёт быструю инициализацию проекта и процесс, при котором человек читает
спеки, планы и тесты — а качество кода обеспечивается механически.

## Принцип

Качество нельзя «попросить» инструкциями — его нужно навязать. Три слоя,
по убыванию надёжности:

1. **Детерминированные гейты (хуки)** — код не проходит дальше, пока не
   пройдут typecheck / lint / тесты. Модель не может их уговорить.
2. **Агенты-ревьюеры** — чистый контекст, чек-лист, режут раздутый код.
3. **Скиллы и инструкции** — задают процесс, но контролем не являются.

Точка контроля человека смещается с «прочитать весь дифф» на «утвердить
план и прочитать тесты».

## Установка

В Claude Code:

```
/plugin marketplace add just3is-dev/agent-dev-kit
```

```
/plugin install agent-dev-kit@agent-dev-kit
```

(при разработке самого кита можно подключать локальный клон:
`/plugin marketplace add /путь/к/agent-dev-kit`)

Плагин можно держать установленным глобально: в проектах без контрактных
скриптов хуки молча бездействуют и ничему не мешают. Для установки на
уровень проекта — те же команды с `--scope project` через CLI
(`claude plugin marketplace add … --scope project`, затем
`claude plugin install … --scope project` из папки проекта).

Команды плагина вызываются с префиксом: `/agent-dev-kit:project-init`,
`/agent-dev-kit:spec`, `/agent-dev-kit:plan`, `/agent-dev-kit:work`
(в тексте ниже для краткости — без префикса). Набор `/` в Claude Code
показывает точные имена.

## Как этим пользоваться: полный цикл

### 1. Инициализация проекта — `/project-init [путь]`

Запускается в пустой директории или поверх существующего проекта:

- спросит стек (`nextjs` / `nestjs` / `python-service` / другой) и описание;
- спросит, как устроен процесс, и запишет плоские атрибуты процесса в
  `adk.config.json` в корне проекта (перечень и дефолты —
  [docs/config.md](docs/config.md)). Пресеты «личный» / «командный» /
  «только вручную» — лишь ярлыки готовых ответов в диалоге: в файл попадают
  атрибуты, имени пресета в нём нет. Конфиг коммитится (политика —
  разделяемая правда команды), существующий `adk.config.json` никогда
  не перезаписывается;
- пустой проект создаст штатным генератором стека (create-next-app,
  nest new, uv init);
- наложит контракт: `scripts/check`, `scripts/test`, `scripts/fix`,
  CI-workflow, CLAUDE.md, .gitignore;
- **проверит контракт вживую** — инициализация не завершается с падающими
  проверками;
- сделает git init и первый коммит, предложит создать GitHub-репозиторий.

После этого гейты уже активны.

### 2. Спека — `/spec <идея фичи>`

Превращает идею в спеку `docs/specs/NNN-<слаг>.md`: зачем, что делаем
(наблюдаемое поведение), границы (что сознательно НЕ делаем), проверяемые
критерии приёмки. Задаст 2–3 вопроса, если в идее не хватает ключевого.
Вы читаете, правите, утверждаете — статус становится `approved`.

### 3. План — `/plan [спека]`

Planner-агент декомпозирует спеку на атомарные задачи (один PR ≤ ~300 строк
диффа, самодостаточная формулировка, проверяемый DoD, явные зависимости).
План показывается **вам в чате — до создания чего-либо в GitHub**. После
вашего апрува создаются milestone `SPEC-NNN` и issues (по одному на задачу)
через `gh`. Нет GitHub — план сохранится в `docs/plans/` с чекбоксами.

### 4. Выполнение — `/work [номер issue]`

Одна задача от issue до PR:

```
issue → ветка issue-N-слаг → падающие тесты из DoD → минимальная реализация
      → зелёные check и test → draft-PR (Closes #N) → reviewer-агент
      → APPROVE → PR переводится в ready (до этого merge физически недоступен)
```

Без номера берётся следующий незаблокированный issue текущего milestone.
При вердикте REQUEST_CHANGES агент чинит замечания и перезапускает ревью;
после двух неудачных кругов зовёт вас — продолжение одной командой
`/review` (она авторизует дополнительный круг: доработка по прошлым
вердиктам → свежий круг → при APPROVE PR переводится в ready).

Побочный эффект: `/work` попутно ведёт журнал прогона в
`.adk/logs/issue-<N>.jsonl` (старт, каждый круг ревью, финальный итог) —
на нём строится сводка `/stats`.

**Политика merge: только после APPROVE.** Draft-PR смержить нельзя
(GitHub), ready PR становится единственным путём — через вердикт APPROVE,
а хук разрешает `gh pr merge` только для ready. Мержите вы — читая спеку,
тесты и вердикт, — либо `/autopilot`: он проходит очередь issues (свежий
субагент на задачу), мержит ready-PR сам (squash: один issue = один коммит в main), а застрявшие помечает
`needs-human` и присылает уведомление.

### 5. Повторяйте `/work`, пока milestone не закрыт.

### 6. На границе вехи — `/consolidate`

После закрытия milestone (или крупной группы задач) — уборка межзадачного
дрейфа: read-only инвентаризация собирает кандидатов (дубли между PR,
разъехавшиеся паттерны, мёртвый код, несделанные «мелочи» из вердиктов
ревьюера), вы выбираете из списка, выбранное становится обычными мелкими
задачами под `/work` с правилом «поведение не меняется, тесты только
перемещаются». Свободный «отрефакторь проект» этим процессом сознательно
запрещён.

### Багфиксы — короткий путь

Багу спека не нужна: создайте issue с шагами воспроизведения и ожидаемым
поведением — и сразу `/work <номер>`. Железное правило (зашито в `/work` и
скилл tdd): первый шаг — падающий тест, воспроизводящий баг; без
воспроизведения фикс не начинается. Тест остаётся навсегда как защита
от регрессии.

Тело баг-issue обязано содержать строку «Сбежал от: <гейт>» — какой гейт
должен был поймать дефект до того, как его увидел человек: `check` (тесты
проходили, но статическая проверка/типизация не поймала), `test`
(упавший сценарий не был покрыт тестом), `reviewer` (тест был, но ревьюер
пропустил дефект в диффе) или `процесс` (гейт тут бессилен — решение или
коммуникация). Это петля обратной связи: `/consolidate` на границе вехи
агрегирует распределение по гейтам и предлагает усилить самый «текущий».

### Если план оказался неверен

Реализация разошлась со спекой или планом — агент обязан остановиться и
предложить правку, а не «доделать как понял» (правило в `/work`). Повторный
`/plan` по той же спеке работает как перепланирование: сверяет issues с
фактом и предлагает дельту, дубли не плодит.

## Справочник

### Команды

| Команда | Что делает |
|---|---|
| `/project-init [путь]` | Инициализация проекта: каркас стека, контракт, гейты, CI, git |
| `/spec <идея>` | Идея → самодостаточная спека с критериями приёмки |
| `/plan [спека]` | Спека → план атомарных задач → (после апрува) milestone + issues |
| `/work [issue]` | Задача → ветка → TDD → гейты → PR → вердикт ревьюера |
| `/consolidate [область]` | Инвентаризация межзадачного мусора → апрув → задачи рефакторинга. Запускать на границах вех |
| `/review [PR/issue]` | Следующий раунд ревью: доработка по прошлым вердиктам → свежий круг → APPROVE → ready. Явный вызов снимает лимит «двух кругов» |
| `/autopilot [лимит]` | Очередь issues автономно: свежий субагент на задачу, merge только ready-PR; застрявшие — метка needs-human + уведомление |
| `/stats` | Сводка по журналу прогонов: всего задач, средние круги ревью, доля застреваний и причины, динамика по неделям |

### Скиллы

Скиллы агент подхватывает сам по описанию задачи; ссылаться на них можно
и явно («сделай по скиллу tdd»).

| Скилл | Когда срабатывает | Суть |
|---|---|---|
| `decompose` | Планирование работ по спеке | Критерии атомарности задачи: один читаемый PR, самодостаточная формулировка, проверяемый DoD, минимум зависимостей, система зелёная после каждой задачи. Формат постановки и анти-паттерны («сделать всё остальное», горизонтальная нарезка, задачи «на будущее») |
| `tdd` | Реализация любой задачи с кодом | Тесты до кода: DoD → падающие тесты → минимальная реализация → уборка. Тестировать поведение, не внутренности; моки только на границах; запрещено ослаблять/скипать тесты ради прохождения гейта |
| `adr` | Неочевидный технический выбор | Когда писать ADR (реальные альтернативы, отступление от дефолта, дорого откатить), когда не писать (очевидное, пересказ кода). Одна страница: контекст → решение → последствия. Решение изменилось — новый ADR со ссылкой supersedes |
| `stack-choice` | Старт проекта, новый сервис/язык | Дефолты: Next.js / NestJS / React Native; отступление — по задаче и с ADR. Железное правило: добавил язык или сервис — в том же PR расширь scripts/check\|test и CI. Код вне контракта = непроверяемый код |
| `consolidate` | Границы вех (закрыт milestone) | Агенты «одна задача — одна сессия» оптимизируют локально; межзадачный дрейф (дубли между PR, разные способы одного и того же, мёртвый код, хвосты ревью) не видит никто. Инвентаризация read-only → список кандидатов с оценкой польза/риск/дифф → выбор человека → мелкие задачи с железными правилами: поведение не меняется, тесты только перемещаются |

### Модели по ролям

Принцип: дорогая модель — туда, где ошибка размножается; дешёвая — туда,
где ошибку поймают гейты ниже по конвейеру.

| Роль | Модель | Как задано |
|---|---|---|
| Ревьюер | Opus | жёстко (frontmatter агента) |
| Планировщик | Opus | жёстко (frontmatter агента) |
| Инвентаризатор /consolidate | Opus | инструкция команды |
| Спека (/spec) | Opus | рекомендация: выполнять в Opus-сессии |
| Исполнитель (/work, субагенты /autopilot) | модель сессии | рекомендация: Sonnet |

### Агенты

| Агент | Роль |
|---|---|
| `planner` | Спека → план атомарных задач. Изучает реальную структуру кода, режет вертикально, показывает покрытие критериев приёмки задачами. Кода не пишет |
| `reviewer` | Ревью диффа с чистым контекстом. Чек-лист: соответствие задаче (ничего лишнего/недоделанного) → раздутость (дубли, лишние абстракции, мёртвый код) → тесты (поведение, без заглушек, ничего не ослаблено) → корректность (граничные случаи) → доки. Вердикт APPROVE / REQUEST_CHANGES с замечаниями file:line |

### Гейты (хуки)

Работают автоматически, настройки не требуют:

| Хук | Момент | Что делает |
|---|---|---|
| `post-edit-check` | После каждого Edit/Write | `scripts/check <файл>`; ошибки возвращаются агенту с требованием исправить |
| `stop-test` | Агент завершает работу | `scripts/test`; красные тесты не дают закончить. Бегут только при изменениях в рабочем дереве; успешный прогон кэшируется по хэшу диффа |
| `bash-guard` | Перед каждой Bash-командой | Запрещает `git commit --no-verify`, force push в main/master и `gh pr merge` черновиков (merge только для ready-PR, т.е. после APPROVE; непроверяемый статус = запрет). Перед `git commit` сканирует изменения на секреты (ключи AWS/GitHub/Slack/Google, `sk-*`, приватные ключи) и блокирует коммит `.env`. При `conventions.commitStyle=conventional` валидирует заголовок PR на `gh pr create`/`gh pr edit`: формат `<commitType>[(scope)]: <суть> (#N)`, commitType — по label issue (`types.*` конфига; выключается `conventions.externalTitleLint=true`) |

Плюс серверный гейт: `/project-init` предлагает включить branch protection —
merge в main только через PR с зелёным CI, прямые пуши запрещены. Его не
обойти даже локальным саботажем хуков.

### Уведомления

Чтобы не сидеть и не проверять сессию вручную, кит шлёт локальные
уведомления (macOS `osascript`, Linux `notify-send`):

| Событие | Когда приходит |
|---|---|
| «Claude ждёт вашего ответа» | Немедленно: запрос разрешения или простой в ожидании ввода (hook Notification) |
| «Задача завершена, гейты зелёные» | Ход агента закончился успешно **и** длился дольше порога — короткие реплики живого диалога не дзинькают. Порог: `ADK_NOTIFY_MIN_SECONDS`, по умолчанию 45 с |

Уведомление о завершении не приходит, пока Stop-гейт возвращает агента
дорабатывать красные тесты — «завершено» означает «действительно готово».

### Контракт команд

Мультистековость держится на контракте ([docs/contract.md](docs/contract.md)):
каждый проект обязан иметь `scripts/check [файлы...]`, `scripts/test`,
`scripts/fix [файлы...]`. Хуки и CI зовут только их и не знают стека.
Реализации генерируются из `templates/<стек>/` при инициализации; для
нового стека реализация пишется по образцу с той же семантикой.

### Монорепа

Для фронт+бэк одного продукта монорепа предпочтительна: вертикальная задача
(эндпоинт + UI + типы) — это один PR, а не пара синхронизируемых PR в двух
репозиториях. Устройство: каждый пакет (`apps/web`, `apps/api`,
`services/ml`, …) несёт свой пакетный контракт из шаблона своего стека,
а в корне живёт диспетчер из `templates/monorepo/` — он находит пакеты по
наличию у них `scripts/check` и маршрутизирует проверки по путям файлов.
Хук проверок находит ближайший пакетный контракт сам, Stop-гейт гоняет
корневой `scripts/test` по всем пакетам. Новый пакет со своими скриптами
подхватывается автоматически, отдельные репозитории оправданы только для
действительно разных продуктов. `/project-init` умеет вариант `monorepo`.

## Состав репозитория

```
.claude-plugin/   манифест плагина и marketplace для локальной установки
hooks/            гейты: PostToolUse → check, Stop → test, PreToolUse →
                  запреты; плюс журналирование прогонов и агрегация
                  (adk-log.sh, adk-stats.sh) и AC-трассируемость (ac-check.sh)
commands/         /project-init, /spec, /plan, /work, /review, /autopilot,
                  /stats, /consolidate
agents/           planner, reviewer
skills/           decompose, tdd, adr, stack-choice, consolidate
templates/
  base/           CLAUDE.md, gitignore
  process/        шаблоны SPEC и ADR
  nextjs/         scripts/check|test|fix (tsc, eslint, vitest) + ci.yml
  nestjs/         то же, тесты через jest
  python-service/ ruff, mypy, pytest (окружение uv) + ci.yml
  monorepo/       корневые скрипты-диспетчеры по пакетам + ci.yml
docs/contract.md  контракт команд проекта
docs/config.md    таблица атрибутов adk.config.json и их дефолтов; сам
                  конфиг создаётся `/project-init` в корне проекта
docs/adr/         архитектурные решения (ADR), создаются по скиллу adr
docs/specs/       спеки фич, создаются `/spec`
docs/plans/       планы задач без GitHub-issues, создаются `/plan`
scripts/, tests/  собственный контракт кита: смоук-тесты всех хуков и диспетчера
```

Кит ест свой же корм: у него есть собственные `scripts/check` и
`scripts/test`, так что при доработке плагина его же гейты проверяют
правки хуков. В `scripts/check` кита это включает и проверку
трассируемости `AC → тест` (`hooks/scripts/ac-check.sh . tests/run.sh`) —
та же конвенция, что кит требует от проектов, которые инициализирует.
