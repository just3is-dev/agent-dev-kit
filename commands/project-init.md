Инициализируй проект под процесс agent-dev-kit. Шаблоны: `${CLAUDE_PLUGIN_ROOT}/templates/`,
контракт команд описан в `${CLAUDE_PLUGIN_ROOT}/docs/contract.md`.

## Шаги

1. **Осмотрись.** Целевая директория — `$ARGUMENTS` или текущая. Определи:
   проект пустой или существующий, какой стек уже виден (package.json,
   pyproject.toml и т.д.), есть ли git.

2. **Спроси недостающее** одним вопросом через AskUserQuestion:
   - форма (`nextjs` / `nestjs` / `python-service` / `swift-ios` /
     `monorepo` / другой стек) — только если не очевидна из содержимого;
   - для монорепы — какие пакеты нужны сразу (например: фронт + бэк);
   - название и одно предложение описания — только если проект пустой.

3. **Конфиг процесса — `adk.config.json`.** Если файл `adk.config.json` в
   корне проекта уже есть — не трогай и не перезаписывай его, пропусти этот
   шаг и скажи об этом в итоговом отчёте (конфиг — разделяемая правда
   команды, менять его можно только явным коммитом, не инициализацией).
   Если файла нет — спроси через AskUserQuestion, как устроен процесс.
   Варианты ответа — три пресета-ярлыка (готовые наборы значений, чтобы не
   отвечать на десяток вопросов) плюс ручная настройка:
   - «личный» — агенты пишут и мержат сами: `policies.merge` =
     `agent-after-approve`, `policies.review.humanApprovalRequired` = `false`,
     `policies.autopilot.enabled` = `true`, `policies.autopilot.canMerge` =
     `true`;
   - «командный с обязательным человеческим ревью»: `policies.merge` =
     `human-review-required`, `policies.review.humanApprovalRequired` =
     `true`, `policies.autopilot.enabled` = `true`,
     `policies.autopilot.canMerge` = `false`;
   - «только вручную» — merge только руками человека: `policies.merge` =
     `human-only`, `policies.review.humanApprovalRequired` = `true`,
     `policies.autopilot.enabled` = `false`;
   - «настроить вручную» — пройдись по атрибутам из
     `${CLAUDE_PLUGIN_ROOT}/docs/config.md` и спроси значения.
   Ответы запомни, но файл здесь НЕ создавай: запись — при наложении
   шаблонов (шаги 5–6), после каркаса стека, потому что генераторы вроде
   `create-next-app` требуют пустую директорию и с посторонним файлом
   откажутся работать. Пресет — только ярлык диалога: имя пресета в файл
   не записывается и в рантайме не существует.

4. **Пустой проект — сначала каркас стека штатным генератором**, не выдумывай
   структуру сам: `npx create-next-app@latest` / `npx @nestjs/cli new` /
   `uv init`. Флаги подбирай неинтерактивные. После генераторов удали
   вложенные `.git`, которые они создают (create-next-app делает это
   молча) — иначе файлы пакета не попадут в репозиторий проекта.
   У `swift-ios` штатного CLI-генератора нет: минимальный каркас
   (`project.yml` для XcodeGen + точка входа приложения) напиши по месту
   под конкретный проект и сгенерируй `.xcodeproj` через
   `xcodegen generate` — шаблон кита сознательно везёт только контракт,
   CI и конфиг форматтера, не диктуя структуру проекта (см. ADR).

5. **Наложи шаблоны (одиночный стек):**
   - `templates/base/CLAUDE.md` → `CLAUDE.md`; заполни все `{{плейсхолдеры}}`
     реальными значениями, секцию «Специфика проекта» — фактами об этом проекте
     (или удали, если добавить нечего);
   - `templates/base/gitignore` → дополни существующий `.gitignore`
     недостающими строками (не затирай его);
   - запиши `adk.config.json` в корень проекта — плоский набор атрибутов
     из ответов шага 3 (перечень и дефолты —
     `${CLAUDE_PLUGIN_ROOT}/docs/config.md`). Структура файла — вложенный
     JSON, как в примере `docs/config.md` («плоский» — про модель
     независимых атрибутов, а не про ключи с точками). Файл
     создавай всегда, даже если все выбранные значения совпадают с
     дефолтами: явная запись фиксирует политику как осознанный выбор
     (случай «файл уже был» шаг 3 уже исключил — тогда записи нет вовсе).
     Конфиг коммитится вместе с остальной инициализацией, в отличие от
     журнала `.adk/`, который гитигнорится;
   - `templates/<стек>/scripts/*` → `scripts/`, сделай исполняемыми;
   - `templates/<стек>/ci.yml` → `.github/workflows/ci.yml`;
   - для `swift-ios` дополнительно `templates/swift-ios/swift-format` →
     `.swift-format` в корень проекта (в шаблоне имя без точки, чтобы
     файл не терялся в листингах и архивах). Контракту нужен тулчейн
     Xcode 16+ (`swift format` — его сабкоманда). Существующий проект
     с тестами в XCTest-таргетах `.xcodeproj` или с workspace
     (CocoaPods) — расширь `scripts/test` по месту: шаблон гоняет
     тесты только SPM-пакетов и собирает только `-project` (ADR-006);
   - `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/ac-check.sh` → `scripts/ac-check`, сделай исполняемым —
     хелпер AC-трассируемости; шаблонный `scripts/check` уже вызывает его
     хвостом в полном прогоне (без аргументов-файлов), если он исполняем.
     Скрипты генерируются из шаблонов и не знают путь к плагину, поэтому
     копируем сам файл, а не ссылаемся на `${CLAUDE_PLUGIN_ROOT}`.
   - `docs/` не создавай заранее — директории появятся с первой спекой/ADR.

6. **Монорепа:**
   - структура: `apps/<имя>` для приложений (фронт, бэк), `services/<имя>`
     для отдельных сервисов; каждый пакет создаётся штатным генератором
     своего стека;
   - в каждый пакет — `templates/<стек этого пакета>/scripts/*`
     (исполняемые). Это пакетный контракт: хук проверок находит его сам;
   - в корень — `templates/monorepo/scripts/*` (диспетчер: находит пакеты
     по наличию у них scripts/check и маршрутизирует по путям файлов)
     и `templates/monorepo/ci.yml`; блок установки зависимостей в CI
     подстрой под фактические пакеты;
   - в корень — также `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/ac-check.sh` → `scripts/ac-check`
     (тот же хелпер, что и для одиночного стека; `docs/specs` в монорепе
     общий на корне, поэтому копия одна, а не на пакет);
   - в корень — также `adk.config.json` из ответов шага 3 (правила те же,
     что в шаге 5: создаётся всегда, существующий не перезаписывается;
     конфиг в монорепе один, на корне);
   - `CLAUDE.md` — один, в корне: список пакетов с одним предложением
     о каждом; правило «новый пакет обязан получить свой scripts/check|test|fix,
     корневой диспетчер подхватит его автоматически».

7. **Другой стек** (не из шаблонов): возьми ближайший шаблон за образец и
   напиши реализацию контрактных скриптов под инструменты этого стека сам,
   соблюдая семантику из contract.md (check по файлам — быстрый; test с
   пустым набором тестов — не провал; fix молчалив; полный прогон check
   без аргументов вызывает `scripts/ac-check .`, если он исполняем —
   скопируй его так же, как в шаге 5).

8. **Проверь контракт вживую.** `./scripts/check` и `./scripts/test` должны
   реально отработать из корня (поставь dev-зависимости, если генератор их
   не поставил: для node-стеков как минимум typescript, eslint, prettier и
   тест-раннер). В монорепе убедись, что диспетчер видит все пакеты (вывод
   `── check: <пакет>` для каждого). Не завершай инициализацию с падающим
   контрактом — это фундамент всех гейтов.

9. **Git и сервер репозитория.** Сначала определи ветку: есть ли у проекта
   GitHub remote, созданный до этой инициализации. Есть — это
   **существующий репозиторий**: его серверные настройки управляются не
   нами, только сверка без изменений (см. ниже). Нет (репозитория нет
   вовсе или он локальный, remote появится сейчас) — **новый репозиторий**,
   настройки применяем.

   **Новый репозиторий — применяем настройки.** Сначала — **шаблоны issue
   `.github/ISSUE_TEMPLATE/*` из блока `types`** (тоже SPEC-002 AC-6, но
   это локальные файлы, не `gh api`: создаются и без remote — до первого
   коммита, чтобы попасть в него): люди в команде создают issues в том же
   формате, что и агенты, — `/work` читает тип по label и ожидает
   обязательные поля типа, в issue, заведённом человеком без шаблона, он
   их не найдёт. По одному шаблону на каждый тип из `types.*`; значения
   атрибутов читай через `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-config.sh`
   (например `adk-config.sh types.bug.label type:bug`; перечень типов и
   дефолты — `${CLAUDE_PLUGIN_ROOT}/docs/config.md`), а не переписывай из
   доков руками — конфиг проекта мог их переопределить. Для каждого типа:
   - имя файла — имя типа (`task.md`, `bug.md`, …): label вида `type:task`
     в имя файла не годится — двоеточие в именах файлов невалидно на
     Windows;
   - front matter: `name:` и `labels:` — из `types.<имя>.label`, `about:` —
     одно предложение о назначении типа (без `name:` и `about:` GitHub не
     покажет шаблон в чузере создания issue);
   - тело — секции из `types.<имя>.requiredFields`, в порядке перечисления;
     пустой или отсутствующий `requiredFields` (дефолтный `consolidate`) —
     одна свободная секция описания задачи: шаблон всё равно нужен, чтобы
     чузер вешал label типа;
   - для `bug` тело в том числе содержит строку `Сбежал от: <гейт>` —
     именно её агрегирует `/consolidate` в распределение сбежавших
     дефектов по гейтам.

   Для дефолтного набора типов получаются четыре шаблона: `task`
   (`type:task`), `bug` (`type:bug`), `fastFollow` (`type:fast-follow`),
   `consolidate` (`type:consolidate`). Существующие файлы в
   `.github/ISSUE_TEMPLATE/` не перезаписывай: если шаблон с таким именем
   уже есть и отличается от генерируемого — оставь его как есть и сообщи
   пользователю о расхождении в итоговом отчёте; если совпадает — просто
   оставь, сообщать не о чем (принцип спеки SPEC-002: существующее не
   перезаписывается).

   Если репозитория нет — `git init -b main` и первый коммит. Спроси про
   GitHub: если нужен remote — предложи `gh repo create`. Сразу после
   создания remote настрой сервер по конфигу (SPEC-002 AC-6) — серверный
   гейт, который не обойти локально:
   - **allowed merge methods** — по производному методу приземления:
     `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-config.sh --merge-method`
     выводит его из пары `conventions.squash` × `conventions.branchUpdate`
     (сам метод в конфиге не хранится — не пытайся вычислить его сам,
     используй вывод скрипта). Разреши только этот метод, запрети два
     остальных: `gh api -X PATCH repos/{owner}/{repo}` с полями
     `allow_squash_merge` / `allow_rebase_merge` / `allow_merge_commit`,
     где `true` — ровно у одного, соответствующего выводу
     (`squash-merge` → `allow_squash_merge`, `rebase-merge` →
     `allow_rebase_merge`, `merge-commit` → `allow_merge_commit`);
   - тем же вызовом — `delete_branch_on_merge=true`: ветки после
     приземления удаляет сервер (`--delete-branch` в командах остаётся
     страховкой для репозиториев без этой настройки);
   - **branch protection согласно `policies`**: merge только через PR с
     зелёным required-чеком `gates`, прямые пуши и force push в main
     запрещены — `gh api -X PUT repos/{owner}/{repo}/branches/main/protection`
     с `required_status_checks.contexts=["gates"]`,
     `allow_force_pushes=false`, `enforce_admins=false`. Если
     `adk-config.sh policies.review.humanApprovalRequired false` даёт
     `true` — добавь `required_pull_request_reviews` с
     `required_approving_review_count=1` (обязательный человеческий approve;
     заодно GitHub начнёт заполнять `reviewDecision`, на который опирается
     политика merge `human-review-required` — см. `docs/config.md`); при
     `false` — required reviews не включай, чтобы владелец мог мержить
     без апрувов.

   **Существующий репозиторий — только сверка, без изменений.** Принцип
   SPEC-002 «существующее не перезаписывается»: настройки читаются,
   расхождения с конфигом сообщаются, не меняется ничего. В этой ветке
   запрещён любой изменяющий вызов `gh api` (`-X PATCH` / `-X PUT` /
   `-X POST` / `-X DELETE`) и любая перезапись существующих файлов:
   - прочитай фактические настройки только читающими вызовами:
     `gh api repos/{owner}/{repo}` — allowed merge methods
     (`allow_squash_merge` / `allow_rebase_merge` / `allow_merge_commit`)
     и `delete_branch_on_merge`;
     `gh api repos/{owner}/{repo}/branches/main/protection` — branch
     protection (ответ 404 — protection не настроена: не сбой, а факт для
     сверки); наличие файлов `.github/ISSUE_TEMPLATE/` по типам из
     `types.*`;
   - ожидаемое вычисли по конфигу тем же способом, что и для нового
     репозитория: метод приземления — `adk-config.sh --merge-method`,
     protection — по `policies`, шаблоны — по `types`;
   - каждое расхождение покажи пользователю строкой «ожидается по
     конфигу / фактически»;
   - расхождение — не ошибка инициализации: команда завершается успешно,
     список расхождений уходит в итоговый отчёт (шаг 10). Полная
     диагностика применимости кита к существующему проекту — открытый
     вопрос SPEC-002, здесь только сверка настроек.

10. **Итог пользователю:** что создано; создан ли `adk.config.json` или
    существующий оставлен нетронутым (шаг 3); для существующего
    репозитория — список расхождений сверки настроек (шаг 9) или «настройки
    совпадают с конфигом»; гейты уже активны (проверки
    после каждой правки, тесты перед завершением работы); дальше процесс:
    `/spec` → `/plan` (апрув → issues) → `/work`.
