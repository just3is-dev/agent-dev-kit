---
description: Запустить следующий раунд ревью PR (доработка по прошлым вердиктам + свежий круг)
argument-hint: "[номер PR или issue; по умолчанию PR текущей ветки]"
---

Проведи следующий раунд ревью. Явный вызов этой команды — авторизация
человека на дополнительный круг: лимит «два круга» из /work на него
не распространяется.

Нотация ниже: `<N>` — номер issue, `<PR>` — номер pull request.

1. **Определи PR**: `$ARGUMENTS` (номер PR или issue — найди PR по ветке
   `issue-<N>-*` или по `Closes #N`), иначе PR текущей ветки
   (`gh pr view`). Нет PR — скажи об этом и остановись. Запомни исходную
   ветку по имени (`git branch --show-current`) — команда вернёт дерево
   на неё в конце, независимо от того, сколько раз шаги 3 и 5
   переключатся на ветку PR.

2. **Прочитай историю кругов**: `gh pr view <PR> --comments` — все прошлые
   вердикты. Собери список незакрытых замечаний уровней «блокер» и «важно».

3. **Сначала доработка, потом ревью.** Встань на ветку PR явным `gh pr
   checkout <PR>` — безусловно, даже если чинить нечего: шаг 4 (ревью)
   идёт по этому checkout, reviewer-агент читает дифф локально (не
   только через `gh`), и должен видеть ветку PR, а не то, что было до
   вызова `/review` (при первом круге `/review` по чужому PR незакрытых
   замечаний нет по определению, а ревью всё равно нужно). Дерево пока
   не возвращай — единый возврат для всей команды в конце шага 5. Если
   незакрытые блокеры/важно есть — исправь их по обычным правилам (скилл
   tdd, гейты зелёные, коммиты в ветку PR) и запушь. Если все замечания
   уже закрыты коммитами — коммитить нечего, сразу переходи к ревью.

4. **Свежий круг ревью**: запусти reviewer-агента (agent-dev-kit:reviewer)
   с чистым контекстом. Для повторного круга дай ему фокус: проверить
   закрытие замечаний предыдущего вердикта И поискать новые проблемы,
   внесённые самими фиксами (частый паттерн), плюс быстрый проход по
   полному чек-листу.

5. **По вердикту**: запость комментарием в PR. APPROVE → перед переводом
   в ready проверь актуальность ветки по каноническому рецепту шага 6
   `/work` (AC-8 SPEC-002: отставание фактом из git, актуализация
   способом из `conventions.branchUpdate` (дефолт `rebase`), после неё
   обязательный перегон гейтов — переводить в ready без него запрещено;
   конфликт — `mergeable=CONFLICTING` или конфликт при самой
   актуализации, `--abort` — остановись, его разрешает человек).
   Отличие `/review` от канона — **checkout**: дерево уже на ветке PR
   (шаг 3 встал на неё безусловно) — без этого гарантии проверка с
   чужого HEAD дала бы ложное «актуальна», а актуализация с него затёрла
   бы ветку PR (та же оговорка — в `/autopilot`). Отставание считается
   как в каноне, от HEAD (`git fetch origin && git rev-list --count
   HEAD..origin/main` — больше нуля значит ветка отстала).

   Ветка актуальна и гейты зелёные — `gh pr ready <PR>`
   и отчёт «готов к merge». REQUEST_CHANGES → PR остаётся draft; отчёт
   с замечаниями и твоей оценкой: проблема в коде (тогда следующий
   `/review` после правок), в постановке issue (предложи правку) или
   ревьюер требует неразрешимого (человек решает merge вопреки).
   Три и более кругов на одной задаче — явно скажи, что это сигнал
   смотреть на постановку, а не на код.

   **Возврат дерева**: в любом исходе всей команды (ready, REQUEST_CHANGES,
   конфликт, остановка) верни рабочее дерево на исходную ветку,
   запомненную в шаге 1 (`git checkout <исходная ветка>` — по имени, а не
   `git checkout -`: `gh pr checkout <PR>` пишет запись в reflog, даже
   если дерево уже стоит на нужной ветке, и после checkout'а шага 3
   `@{-1}` перестаёт указывать на настоящую исходную ветку) — до вызова
   `/review` дерево могло стоять где угодно, а следующий `/work` начинает
   с `git pull` на текущей ветке.
