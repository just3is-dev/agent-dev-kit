---
description: Запустить следующий раунд ревью PR (доработка по прошлым вердиктам + свежий круг)
argument-hint: "[номер PR или issue; по умолчанию PR текущей ветки]"
---

Проведи следующий раунд ревью. Явный вызов этой команды — авторизация
человека на дополнительный круг: лимит «два круга» из /work на него
не распространяется.

Нотация ниже: `<N>` — номер issue, `<PR>` — номер pull request.

1. **Определи PR**: `$ARGUMENTS` (номер PR или issue — найди PR по ветке
   `issue-<N>-*` или по `Closes #N`), иначе PR текущей ветки
   (`gh pr view`). Нет PR — скажи об этом и остановись. Запомни исходный
   ref (`git symbolic-ref --short -q HEAD || git rev-parse HEAD` — второе
   на detached HEAD, где у первого пустой вывод) — команда вернёт дерево
   на него в конце.

2. **Прочитай историю кругов**: `gh pr view <PR> --comments` — все прошлые
   вердикты. Собери список незакрытых замечаний уровней «блокер» и «важно».

3. **Сначала доработка, потом ревью.** Встань на ветку PR явным `gh pr
   checkout <PR>` — безусловно, даже если чинить нечего: шаг 4 (ревью)
   идёт по этому checkout, reviewer-агент читает дифф локально (не
   только через `gh`), и должен видеть ветку PR, а не то, что было до
   вызова `/review` (при первом круге `/review` по чужому PR незакрытых
   замечаний нет по определению, а ревью всё равно нужно). Дерево пока
   не возвращай — единый возврат для всей команды в конце шага 5. Если
   незакрытые блокеры/важно есть — исправь их по обычным правилам (скилл
   tdd, гейты зелёные, коммиты в ветку PR) и запушь. Если все замечания
   уже закрыты коммитами — коммитить нечего, сразу переходи к ревью.

4. **Свежий круг ревью**: запусти reviewer-агента (agent-dev-kit:reviewer)
   с чистым контекстом. Для повторного круга дай ему фокус: проверить
   закрытие замечаний предыдущего вердикта И поискать новые проблемы,
   внесённые самими фиксами (частый паттерн), плюс быстрый проход по
   полному чек-листу.

5. **По вердикту**: запость комментарием в PR (`gh pr comment`), затем
   залогируй круг тем же вызовом, что шаг 6 `/work` (SPEC-001: каждая
   завершённая через `/review` задача тоже оставляет запись в журнале) —
   с продолжением нумерации кругов задачи, а не с круга 1: прочитай
   журнал (`$ADK_LOGS_DIR/issue-<N>.jsonl`, а если `ADK_LOGS_DIR` не
   задан — `<корень проекта>/.adk/logs/issue-<N>.jsonl`) и возьми
   наибольший `round` среди его строк `event=review` (файла нет или в
   нём нет ни одной такой строки — это круг 1, иначе `<max+1>`):
   `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-log.sh issue-<N>
   event=review round=<номер круга> verdict=<APPROVE|REQUEST_CHANGES> ||
   true` (журнал — наблюдаемость, не гейт: провал записи не блокирует
   задачу).

   APPROVE → перед переводом в ready проверь актуальность ветки по
   каноническому рецепту шага 6 `/work` (AC-8 SPEC-002: отставание
   фактом из git, актуализация способом из `conventions.branchUpdate`
   (дефолт `rebase`), после неё обязательный перегон гейтов —
   переводить в ready без него запрещено; конфликт —
   `mergeable=CONFLICTING` или конфликт при самой актуализации,
   `--abort` — остановись, его разрешает человек). Отличие `/review` от
   канона — **checkout**: дерево уже на ветке PR (шаг 3 встал на неё
   безусловно) — без этой гарантии проверка с чужого HEAD дала бы
   ложное «актуальна», а актуализация с него затёрла бы ветку PR (та же
   оговорка — в `/autopilot`). Отставание считается как в каноне, от
   HEAD (`git fetch origin && git rev-list --count HEAD..origin/main` —
   больше нуля значит ветка отстала).

   Ветка актуальна и гейты зелёные — `gh pr ready <PR>`, затем обнови
   итог задачи тем же способом, что шаг 7 `/work`:
   `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-log.sh issue-<N>
   event=outcome result=merged || true` — новая строка `event=outcome` в
   append-only журнале переопределяет предыдущий итог для
   `adk-stats.sh` (задача, которую `/work` оставил `stuck` после
   `REQUEST_CHANGES`, теперь агрегируется как `merged`). Отчёт — «готов
   к merge». REQUEST_CHANGES → PR остаётся draft; отчёт с замечаниями и
   твоей оценкой: проблема в коде (тогда следующий `/review` после
   правок), в постановке issue (предложи правку) или ревьюер требует
   неразрешимого (человек решает merge вопреки). Три и более кругов на
   одной задаче — явно скажи, что это сигнал смотреть на постановку, а
   не на код.

   **Возврат дерева**: в любом исходе всей команды (ready, REQUEST_CHANGES,
   конфликт, остановка) верни рабочее дерево на ref, запомненный в шаге 1
   (`git checkout <исходный ref>` — по значению, а не `git checkout -`:
   `@{-1}` хранит только последний переход между ветками, а дерево между
   шагом 1 и возвратом может переключаться произвольное число раз
   (checkout шага 3, дальнейшие действия при доработке или ревью) —
   возврат по значению, зафиксированному в шаге 1, от этого не зависит) —
   до вызова `/review` дерево могло стоять где угодно, а следующий `/work`
   начинает с `git pull` на текущей ветке.
