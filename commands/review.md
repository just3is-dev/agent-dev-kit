---
description: Запустить следующий раунд ревью PR (доработка по прошлым вердиктам + свежий круг)
argument-hint: "[номер PR или issue; по умолчанию PR текущей ветки]"
---

Проведи следующий раунд ревью. Явный вызов этой команды — авторизация
человека на дополнительный круг: лимит «два круга» из /work на него
не распространяется.

Нотация ниже: `<N>` — номер issue, `<PR>` — номер pull request.

1. **Определи PR**: `$ARGUMENTS` (номер PR или issue — найди PR по ветке
   `issue-<N>-*` или по `Closes #N`), иначе PR текущей ветки
   (`gh pr view`). Нет PR — скажи об этом и остановись.

2. **Прочитай историю кругов**: `gh pr view <PR> --comments` — все прошлые
   вердикты. Собери список незакрытых замечаний уровней «блокер» и «важно».

3. **Сначала доработка, потом ревью.** Если незакрытые блокеры/важно
   есть — исправь их по обычным правилам (скилл tdd, гейты зелёные,
   коммиты в ветку PR). Если все замечания уже закрыты коммитами —
   переходи сразу к ревью.

4. **Свежий круг ревью**: запусти reviewer-агента (agent-dev-kit:reviewer)
   с чистым контекстом. Для повторного круга дай ему фокус: проверить
   закрытие замечаний предыдущего вердикта И поискать новые проблемы,
   внесённые самими фиксами (частый паттерн), плюс быстрый проход по
   полному чек-листу.

5. **По вердикту**: запость комментарием в PR. APPROVE → перед переводом
   в ready проверь актуальность ветки по каноническому рецепту шага 6
   `/work` (AC-8 SPEC-002: отставание фактом из git, актуализация
   способом из `conventions.branchUpdate` (дефолт `rebase`), после неё
   обязательный перегон гейтов — переводить в ready без него запрещено;
   конфликт — `mergeable=CONFLICTING` или конфликт при самой
   актуализации, `--abort` — остановись, его разрешает человек).
   Отличия `/review` от канона:
   - **checkout**: сперва встань на ветку PR явным `gh pr checkout <PR>`
     — в отличие от `/work`, checkout дерева здесь не определён (команду
     могли вызвать с номером чужого PR, шаг 3 мог обойтись без правок):
     проверка с чужого HEAD даст ложное «актуальна», а актуализация с
     него затёрла бы ветку PR (та же оговорка — в `/autopilot`). После
     checkout отставание считается как в каноне, от HEAD
     (`git fetch origin && git rev-list --count HEAD..origin/main` —
     больше нуля значит ветка отстала);
   - **возврат дерева**: в любом исходе (ready, конфликт, остановка)
     верни рабочее дерево на исходную ветку (`git checkout -`) — до
     вызова `/review` оно могло стоять где угодно, а следующий `/work`
     начинает с `git pull` на текущей ветке.

   Ветка актуальна и гейты зелёные — `gh pr ready <PR>`
   и отчёт «готов к merge». REQUEST_CHANGES → PR остаётся draft; отчёт
   с замечаниями и твоей оценкой: проблема в коде (тогда следующий
   `/review` после правок), в постановке issue (предложи правку) или
   ревьюер требует неразрешимого (человек решает merge вопреки).
   Три и более кругов на одной задаче — явно скажи, что это сигнал
   смотреть на постановку, а не на код.
