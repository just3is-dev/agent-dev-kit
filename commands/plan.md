Построй план работ по спеке ($ARGUMENTS или последняя approved в docs/specs/)
и после апрува пользователя преврати его в GitHub issues.

1. **Запусти planner-агента** (agent-dev-kit:planner), передав ему путь к
   спеке. Если спека не approved или без проверяемых критериев приёмки —
   остановись и скажи об этом.
2. **Покажи план пользователю в чате целиком** — задачи, DoD (со ссылкой на
   номер AC, который каждый пункт закрывает), зависимости, покрытие
   критериев приёмки в формате «AC-N → задачи». НИЧЕГО не создавай в GitHub
   до явного апрува.
   Пользователь просит изменить — правь план (через planner или сам) и
   показывай снова.
3. **После апрува** — создай задачи в GitHub через gh:
   - проверь `gh auth status` и наличие remote; если GitHub недоступен —
     fallback: сохрани план в `docs/plans/NNN-<слаг>.md` с чекбоксами и скажи,
     что issues можно создать позже;
   - milestone: заголовок — первая строка файла спеки без `# `, байт в
     байт (`SPEC-NNN: Название`); регистр и формулировка не могут
     разойтись со спекой, потому что источник один:
     `gh api repos/{owner}/{repo}/milestones -f title=... -f description=...`;
   - label типа задачи: имя возьми из конфига проекта —
     `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-config.sh types.task.label type:task`
     (отсутствие конфига или атрибута = дефолт `type:task`, см.
     docs/config.md). Перед созданием issues создай отсутствующий label в
     репозитории: `label_err=$(gh label create <label> 2>&1 >/dev/null)`.
     Раздели исходы: нулевой exit или текст ошибки с «already exists» —
     успех (label уже есть, идемпотентно), молча продолжай к issues; любую
     другую ошибку (например, отказ по правам) не глуши — скажи явно, что
     label не создан и `gh issue create --label` может упасть, и покажи
     текст ошибки. Правило спеки: тип задачи задаётся только label'ом, из
     текста issue не выводится;
   - по issue на задачу: заголовок — название задачи, тело — контекст,
     «Сделать», DoD, зависимости («Blocked by #N»), ссылка на файл спеки;
     `gh issue create --milestone ... --label <label> --title ... --body ...`;
   - тело issue самодостаточно: исполнитель не обязан читать этот чат;
   - после создания issues аннотируй в спеке критерии, тесты которых ещё
     не существуют: `AC-N (ждёт #<issue>)` — номер первого issue,
     добавляющего тег-тест этого AC. Без аннотаций ac-check будет красным
     весь милестоун (issue #54). Правка спеки — обычным PR.
4. **Отчитайся:** номера созданных issues, порядок выполнения с учётом
   зависимостей, команда для старта: `/work` или `/work <номер issue>`.

## Перепланирование

Если milestone по этой спеке уже существует — это перепланирование, а не
новый план: дубли не создавай. Сверь план с фактом (`gh issue list
--milestone ...`, закрытые issues — выполненное) и предложи пользователю
дельту: какие issues добавить, закрыть как неактуальные, переформулировать.
Применяй только после апрува. Если изменилась сама спека — сначала обнови
файл спеки, потом дельту issues. Labels типа действуют только вперёд:
существующие issues задним числом не типизируй, на закрытых issues labels
не переклеивай (граница SPEC-002).
