Построй план работ по спеке ($ARGUMENTS или последняя approved в docs/specs/)
и после апрува пользователя преврати его в GitHub issues.

1. **Найди спеку и её ветку.** Approved-статус спека получает в своей
   ветке (`spec/NNN-<слаг>`, заводит её шаг 3 `/spec`; approved ставит
   шаг 4 `/spec`) — сам PR спеки при этом мог остаться черновиком: с
   issue #172 `/spec` больше не мержит спеку сразу после апрува именно
   для того, чтобы к моменту, когда она попадёт в main, у её критериев
   уже были аннотации «ждёт #N». Из-за этого спека, ждущая `/plan`,
   может не существовать в `docs/specs/` main вообще — сначала проверь
   открытые ветки спек, только потом main:
   - `$ARGUMENTS` — номер/путь спеки: если он совпадает с открытой веткой
     `spec/<номер>-*` (`gh pr list --state open --json
     number,headRefName --search "head:spec/"` или `git ls-remote
     --heads origin 'spec/<номер>-*'`), используй её; иначе ищи файл как
     раньше — в `docs/specs/` main (спека уже смержена).
   - `$ARGUMENTS` не задан — «последняя approved» теперь ищется в двух
     местах: сначала среди открытых веток `spec/*`
     (`gh pr list --state open --json number,headRefName --search
     "head:spec/"`), у каждой прочитай статус файла спеки в самой ветке
     (`git show origin/<ветка>:docs/specs/<файл>.md`, не файл main) —
     approved среди них ровно одна — бери её; несколько — неоднозначность,
     спроси пользователя, какую; ни одной — тогда как раньше, последняя
     approved в `docs/specs/` main (спека уже смержена — обычно
     перепланирование).
   - Дальше по найденной спеке определи режим:
     - **ветка спеки** (найдена веткой из пунктов выше, её PR открыт и не
       смержен) — переключись на эту ветку (`git fetch origin
       spec/NNN-<слаг> && git checkout spec/NNN-<слаг>`, либо заведи
       локальную, отслеживающую origin, если её ещё нет) и дальше работай
       поверх неё, не поверх main. Если у ветки есть PR, но он `CLOSED` (не
       `MERGED` и не открыт) — спека брошена или сломана: остановись и
       спроси пользователя, продолжать ли эту ветку или считать спеку
       неактуальной; не выбирай режим сам.
     - **спека уже в main** (найдена в `docs/specs/` main, ветки нет или
       она смержена) — обратная совместимость со спеками, approved
       которых было проставлено до этого правила, или смерженными
       вручную: работай как раньше, от main, без переключения — шаг 5
       применит для неё старый путь аннотирования.
2. **Запусти planner-агента** (agent-dev-kit:planner), передав ему путь к
   спеке (в текущей рабочей копии — после шага 1 это либо файл в ветке
   спеки, либо файл в main). Если спека не approved или без проверяемых
   критериев приёмки — остановись и скажи об этом.
3. **Покажи план пользователю в чате целиком** — задачи, DoD (со ссылкой на
   номер AC, который каждый пункт закрывает), зависимости, покрытие
   критериев приёмки в формате «AC-N → задачи». НИЧЕГО не создавай в GitHub
   до явного апрува.
   Пользователь просит изменить — правь план (через planner или сам) и
   показывай снова.
4. **После апрува** — создай задачи в GitHub через gh:
   - проверь `gh auth status` и наличие remote; если GitHub недоступен —
     fallback: сохрани план в `docs/plans/NNN-<слаг>.md` с чекбоксами и скажи,
     что issues можно создать позже;
   - milestone: заголовок — первая строка файла спеки без `# `, байт в
     байт (`SPEC-NNN: Название`); регистр и формулировка не могут
     разойтись со спекой, потому что источник один:
     `gh api repos/{owner}/{repo}/milestones -f title=... -f description=...`;
   - label типа задачи: имя возьми из конфига проекта —
     `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/adk-config.sh types.task.label type:task`
     (отсутствие конфига или атрибута = дефолт `type:task`, см.
     docs/config.md). Перед созданием issues создай отсутствующий label в
     репозитории: `label_err=$(gh label create <label> 2>&1 >/dev/null)`.
     Раздели исходы: нулевой exit или текст ошибки с «already exists» —
     успех (label уже есть, идемпотентно), молча продолжай к issues; любую
     другую ошибку (например, отказ по правам) не глуши — скажи явно, что
     label не создан и `gh issue create --label` может упасть, и покажи
     текст ошибки. Правило спеки: тип задачи задаётся только label'ом, из
     текста issue не выводится;
   - по issue на задачу: заголовок — название задачи **без порядкового
     номера плана** («1., 2., …» — внутренняя нумерация плана для
     покрытия AC и ссылок между задачами; в GitHub порядок выражают
     только зависимости «Blocked by #N» и milestone, а номер в заголовке
     устаревает при перепланировании); тело — контекст,
     «Сделать», DoD, зависимости («Blocked by #N»), ссылка на файл спеки;
     `gh issue create --milestone ... --label <label> --title ... --body ...`;
   - тело issue самодостаточно: исполнитель не обязан читать этот чат;
   - после создания issues аннотируй в спеке критерии, тесты которых ещё
     не существуют: `AC-N (ждёт #<issue>)` — номер первого issue,
     добавляющего тег-тест этого AC. Без аннотаций ac-check будет красным
     весь милестоун (issue #54).
5. **Приземли аннотации.** Куда и как коммитить правку спеки — определяет
   режим шага 1:
   - **ветка спеки** — закоммить аннотации в ветку спеки (`git add
     docs/specs/NNN-<слаг>.md && git commit -m "..."`, `git push origin
     spec/NNN-<слаг>`). При отставании от main — актуализируй тем же
     рецептом, что шаг 6 `/work` (`git fetch origin && git rev-list
     --count HEAD..origin/main`; при отставании — способ из
     `conventions.branchUpdate`, затем зелёные `./scripts/check` и
     `./scripts/test` и только потом `git push --force-with-lease`).
     Дальше переведи PR спеки в ready (`gh pr ready <PR>`) и попробуй
     смержить его (squash) тем же способом, каким раньше это делал шаг 4
     `/spec`, — этим шагом спека и аннотации приезжают в main одним
     коммитом: промежуточного состояния, где main содержит approved-
     спеку без покрытых тестов и без аннотаций, не существует по
     построению (issue #172). Отдельного вердикта ревьюера для PR спеки
     не требуется — апрув спеки и плана пользователь уже дал в чате (шаг
     4 `/spec`, шаг 3 здесь), это тот же принцип, что и в исходном шаге 4
     `/spec`. Сам merge проходит через тот же хук `bash-guard.sh` и ту
     же `policies.merge`, что и любой другой `gh pr merge` (docs/config.md):
     при `agent-after-approve` (дефолт) он пройдёт; при
     `human-review-required` или `human-only` хук откажет — тогда PR
     спеки остаётся ready, а не мержится, и это не ошибка: issues уже
     созданы и корректны независимо от того, смержена ли сама спека,
     merge такой спеки отчитай пользователю в шаге 6 как «ждёт человека»
     (тот же смысл, что `result=ready` у `/autopilot`).
   - **спека уже в main** — как раньше: правка спеки обычным PR (main на
     момент её merge уже был зелёным, окно из issue #172 сюда не
     относится).
6. **Отчитайся:** номера созданных issues, порядок выполнения с учётом
   зависимостей, команда для старта: `/work` или `/work <номер issue>`;
   в режиме «ветка спеки» — статус её merge (смержена автоматически, или
   ready и ждёт человека из-за `policies.merge`, см. шаг 5).

## Перепланирование

Если milestone по этой спеке уже существует — это перепланирование, а не
новый план: дубли не создавай. Сверь план с фактом (`gh issue list
--milestone ...`, закрытые issues — выполненное) и предложи пользователю
дельту: какие issues добавить, закрыть как неактуальные, переформулировать.
Применяй только после апрува. Если изменилась сама спека — сначала обнови
файл спеки, потом дельту issues. Labels типа действуют только вперёд:
существующие issues задним числом не типизируй, на закрытых issues labels
не переклеивай (граница SPEC-002).
