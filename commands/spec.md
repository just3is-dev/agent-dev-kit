Преврати идею «$ARGUMENTS» в спеку по шаблону
`${CLAUDE_PLUGIN_ROOT}/templates/process/spec-template.md`.

Спека — артефакт с максимальным рычагом: её ошибки размножаются через
план на все задачи. Если сессия работает на лёгкой модели — честно
предложи пользователю выполнить /spec в сессии с сильной моделью (Opus).

1. **Пойми идею.** Если в ней не хватает ключевого (для кого, какую проблему
   решает, что считается успехом) — задай пользователю не больше 2–3 вопросов
   одним заходом через AskUserQuestion. Не растягивай интервью.
2. **Напиши спеку** в `docs/specs/NNN-<слаг>.md` (NNN — следующий номер;
   директорию создай, если её нет):
   - самодостаточно: читается без истории этого чата;
   - «Что делаем» — наблюдаемое поведение, без технических решений;
   - «Границы» — обязательны: явно назови близкие вещи, которые НЕ делаем;
   - каждый критерий приёмки проверяем — из него можно написать тест;
   - критерии нумеруются последовательно `AC-1, AC-2, …` (формат уже задан
     шаблоном) — номер станет тегом теста, который его закрывает, план и
     реализация ссылаются на него по этому номеру;
   - технические решения, если уже известны и неочевидны, — не в спеку,
     а кандидаты в ADR (скилл adr).
3. **Драфт живёт в ветке, не в main.** Спека — обсуждаемый документ:
   создай ветку `spec/NNN-<слаг>`, закоммить драфт туда и открой
   draft-PR — правки по ходу обсуждения коммитятся в эту ветку.
   В main спека попадает только утверждённой, одним squash-коммитом.
4. **Покажи пользователю** спеку целиком и открытые вопросы. После правок
   пользователь утверждает — поставь статус approved, переведи PR в ready
   и смержи (squash). Дальше — `/plan`.

Спека — живой документ: если при реализации поведение осознанно меняется,
спека обновляется в том же PR, а не остаётся врать.
