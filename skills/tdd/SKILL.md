# Реализация через тесты

Тесты — главный артефакт, который человек читает вместо кода. Поэтому они
пишутся до кода и описывают поведение, а не реализацию.

## Цикл

1. Возьми DoD задачи и преврати каждый пункт в падающий тест. Запусти —
   убедись, что падают по правильной причине (нет поведения, а не опечатка).
2. Напиши минимальную реализацию до зелёного состояния.
3. Приберись (имена, дубли, лишние ветки) — тесты держат.
4. `./scripts/check` и `./scripts/test` зелёные — задача готова к PR.

## Правила для тестов

- **Тестируй наблюдаемое поведение**, не внутренности: вход → выход, вызов
  API → ответ и побочный эффект. Тест, ломающийся от рефакторинга без смены
  поведения, — плохой тест.
- **Название теста — утверждение о поведении** («возвращает 404 для чужого
  ресурса»), читаемое как строка спеки.
- **Никаких тестов-заглушек**: тест без ассертов, тест копирующий реализацию,
  `expect(true)` — хуже отсутствия теста, он создаёт ложное чувство покрытия.
- **Моки только на границах** (сеть, время, внешние сервисы). Мокать свои же
  модули — признак того, что тестируется реализация.
- Нашёл баг по ходу — сначала тест, воспроизводящий его, потом фикс.
- **Тег AC-N, если DoD ссылается на критерий приёмки спеки**: тест, который
  его закрывает, помечается тем же токеном целиком, включая номер спеки —
  `AC-<NNN>-<K>` (например `AC-002-3` для критерия 3 спеки 002) — в имени
  `describe`/`it` для JS/TS-подобных фреймворков (например,
  `it("AC-002-3: ...")`), в строке описания для bash-тестов (например,
  `assert_exit "AC-002-3: ..." ...` или `echo "AC-002-3: ..."`). Номер
  спеки в токене — не украшение: без него одинаковый порядковый номер
  критерия в двух спеках засчитал бы покрытие одной за другую (issue
  #171, обоснование парсера — docs/adr/010-spec-scoped-ac-tokens.md).
  Голый `AC-<K>` без номера спеки по-прежнему принимается (обратная
  совместимость, глобальный пул старого поведения), но `ac-check`
  печатает предупреждение — новый код тегируется префиксной формой. Тег
  без соответствия сути
  критерия — не покрытие, а ярлык для галочки. Покрытие AC-тегами
  проверяет `scripts/ac-check` (копия `hooks/scripts/ac-check.sh` из кита,
  подключённая в `scripts/check` проекта — см. `commands/project-init.md`).

## Запрещено

- Ослаблять или удалять существующий тест, чтобы пройти гейт. Если тест
  устарел из-за осознанной смены поведения — это отдельное изменение,
  явно названное в PR.
- Помечать тесты skip/todo, чтобы «вернуться позже».
