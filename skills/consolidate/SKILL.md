# Консолидация: межзадачный рефакторинг под контролем

Агенты, работающие «одна задача — одна сессия», оптимизируют локально.
Ревьюер ловит дубли внутри одного PR, но межзадачный дрейф не видит никто:
похожие вещи, сделанные в разных задачах по-разному; код, ставший дублем
только после третьего использования; разъехавшийся нейминг. Консолидация —
регулярная уборка этого слоя.

Свободный «отрефакторь проект» запрещён: это худший вид задачи — без
проверяемого DoD и с неограниченным диффом. Только процесс ниже.

## Что ищет инвентаризация

- **Структурные дубли**: одинаковые или почти одинаковые блоки в разных
  модулях (грепать по характерным операциям, не только по именам).
- **Одно и то же разными способами**: два способа читать конфиг, три стиля
  обработки ошибок адаптеров, разные конвенции путей к артефактам.
- **Мёртвый код**: экспорты без потребителей, недостижимые ветки,
  неиспользуемые параметры и поля схем.
- **Лишние абстракции**: обёртки с единственным вызывающим, интерфейсы
  с единственной реализацией без тестовой нужды, прослойки «на будущее».
- **Хвосты**: несделанные «мелочи» из вердиктов ревьюера, TODO, задел из
  fast-follow issues, расхождения доков (ADR/CLAUDE.md) с кодом.
- **Дрейф нейминга**: одна сущность под разными именами в разных модулях.

## Формат кандидата

```
### K<n>. <что консолидируем, одной строкой>
Где: <file:line, все места>
Что не так: <дубль/дрейф/мёртвый код/...>
Предложение: <целевое состояние, 1–2 предложения>
Польза: высокая | средняя | низкая   Риск: низкий | средний | высокий
Дифф: ~<строк>
```

Кандидатов сортировать: сначала высокая польза + низкий риск. Кандидаты
с высоким риском помечать явно — обычно их правильнее не делать.

## Две дополнительные агрегации на границе вехи

Помимо кандидатов на рефакторинг, `/consolidate` перед показом списка
собирает два агрегата (не read-only-инвентаризация кода, а сводка по
процессу):

- **Петля сбежавших дефектов**: распределение метки «Сбежал от: <гейт>»
  по баг-issues области — сколько дефектов сбежало от check, test,
  reviewer или процесса. Самый частый («текущий») гейт — повод предложить
  конкретное усиление (новый паттерн теста, правило ревьюера, пункт
  скилла), а не просто зафиксировать цифру.
- **Выжимка журнала прогонов**: агрегаты `hooks/scripts/adk-stats.sh`
  (задачи, круги ревью, застревания) — журнал сам не коммитится, но его
  выжимку на границе вехи можно закоммитить одним файлом
  `docs/observability/<веха>.md`, с согласия пользователя.

## Железные правила задач консолидации

1. **Поведение не меняется.** Рефакторинг с изменением поведения — это две
   разные задачи, и вторая должна идти обычным путём через спеку/план.
2. **Тесты не редактируются** — только перемещаются вместе с кодом. Правка
   ассертов в задаче консолидации — блокер для ревьюера.
3. **Одна задача — один кандидат** (или связная группа мелких), дифф
   читаем за 10 минут, как требует скилл decompose.
4. **Гейты и ревью — как у любой задачи**: check/test зелёные, ревьюер
   проверяет «дифф без изменения семантики».
5. Инвентаризация — read-only: агент-инвентаризатор ничего не правит.
